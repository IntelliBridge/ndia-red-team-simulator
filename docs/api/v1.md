# HTTP API reference (`/v1/*`)

This page lists every route `redsim.api.app:create_app()` mounts on `main` at
`29db42c` (2026-09-09, wave B0 of the [Phase B plan](../plans/12-phase-b-plan.md),
verified by building the app from this tree and reading its OpenAPI
document): 58 HTTP routes under `/v1`, the 39 Phase A routes plus the 19
Phase B routes that wave B0 mounted behind their real gates as
`501 not_implemented` stubs, plus `GET /health`, `GET /metrics`, the non-prod
debug view `GET /v1/__settings` and the run-events WebSocket. The 19 stubs
are listed under [Phase B routes](#phase-b-routes) with the status "Phase B,
501 until built" and the wave that replaces each one. Wave B1 (the Phase B
library layer: modality runners, the text and detection targets, the
`cw_l2`, `deepfool`, `zoo`, `word_substitution` and `dpatch` attacks, the
endpoint target and predict broker, the training defenses) changed no route;
what it makes visible through the existing catalog routes, and what still
waits for wave B2 admission, is noted section by section. The endpoint
predict contract has its own page,
[Endpoint predict contract](endpoint-contract.md). The OpenAPI document at
`/docs` (non-prod) is the executable contract. For header semantics see
[`docs/architecture/auth.md`](../architecture/auth.md), for the role matrix
its "RBAC" section, and for the design of the ML surface section 17 of the
[product spec](../superpowers/specs/2026-09-08-adversarial-ml-redteam-spec.md).
Where the tree knowingly departs from the spec, the
[accepted divergences](../architecture/ml-vertical.md#accepted-divergences)
list in the ML vertical page records it.

Every route below requires either an `Authorization: Bearer …` header **or** a
valid `redsim_api_session` cookie, except `/health` and `/metrics`, which are
unauthenticated. Cookie-authenticated mutations additionally require the
`X-Redsim-CSRF` header that matches the `redsim_csrf` cookie (see
[CSRF](../architecture/auth.md#csrf-double-submit-cookie)).

Routes are grouped by RBAC tier. Roles rank `viewer` < `scanner` <
`remediator` < `approver` < `admin` (`redsim/api/policy.py`). `viewer` passes
every membership (read) gate and fails every gated action.

| Tier | Gate (`Action`) | Routes |
|---|---|---|
| **Open** | none | `GET /health`, `GET /metrics` |
| **Authenticated** (signed in, no project check) | none | [`GET /v1/ml/capabilities`](#ml-capabilities), [`GET /v1/attacks`](#attack-catalog), [`GET /v1/datasets`](#dataset-catalog), [`GET /v1/defenses`](#defense-catalog), [`GET /v1/scanners`](#scanners) |
| **Membership** (read on the project) | none | [Models (read)](#models), [Runs](#runs), [Campaign record](#campaign-record), [Compare](#compare), [Artifacts](#artifacts), [Findings (read)](#findings), [Projects](#projects), [Orgs](#orgs), [Targets (list)](#targets), [Auth profiles (list)](#auth-profiles), [WebSocket](#websocket) |
| **Scanner+** | `attack.run`, `explain.run`, `report.export` | [`POST /v1/models/{id}/attacks`](#start-a-campaign), [`POST /v1/findings/{id}/explain`](#finding-actions), [`GET /v1/runs/{id}/report.{ext}`](#reports) |
| **Remediator+** | `model.register`, `harden.recommend`, `verify.replay`, `finding.annotate`, `run.cancel` | [`POST /v1/models`](#register-a-model), [`POST /v1/findings/{id}/harden`](#finding-actions), [`POST /v1/findings/{id}/verify`](#verify), [`PATCH /v1/runs/{id}/reviewer-notes`](#reviewer-notes), [`POST /v1/runs/{id}/cancel`](#runs-cancel) |
| **Approver+** | `finding.review` | [`PATCH /v1/findings/{id}/status`](#finding-actions) |
| **Admin** | `target.manage`, `auth_profile.manage`, `audit.verify`, admin membership | [`DELETE /v1/models/{id}`](#delete-a-model), [Targets (write)](#targets), [Auth profiles (write)](#auth-profiles), [Audit verify](#audit), [Logs](#logs), [Project settings](#project-settings) |
| **Phase B, 501 until built** | the gate of the real handler, run before the 501 | the 19 stubs under [Phase B routes](#phase-b-routes) |

Removed with the pentest domain and no longer mounted: `POST /v1/scans`
(answers 404), tickets, agents, fix, `tools/kali`, `exports/vulnfixer`, GitHub
webhooks. Nothing answers on those paths.

Every enqueueing route answers `202` with the same JobHandle,
`{"run_id": "…", "job_ids": ["…"], "status_url": "/v1/runs/<run_id>"}`, after
its audit row is on the chain and its `Run`, `Job` and (for campaigns)
`ml_campaigns` rows exist. Every ML refusal carries the spec 17.3 envelope
described under [Error codes](#error-codes-spec-173).

## Health

### `GET /health`

Liveness probe. Unauthenticated.

```json
{ "status": "ok", "env": "dev", "db_configured": false }
```

`db_configured` is `true` when `REDSIM_DB_URL` is set. `GET /metrics` is the
Prometheus scrape endpoint (it now includes `redsim_ml_campaigns_total` and
`redsim_ml_stage_seconds` alongside the platform counters). `GET /v1/__settings`
is a non-prod debug view of the resolved API settings.

## ML capabilities

### `GET /v1/ml/capabilities`

The feature roster of this deployment, so the web app renders honest disabled
states. **Authenticated.** Never carries the Pythia key or base URL.

```jsonc
{
  "modalities": {
    "image":     { "status": "available", "phase": "A" },
    "tabular":   { "status": "available", "phase": "A" },
    "llm":       { "status": "not_implemented", "phase": "B", "reason": "LLM and endpoint red-teaming is Phase B" },
    "text":      { "status": "not_implemented", "phase": "B", "reason": "…" },   // library on main since wave B1, admitted in wave B2
    "detection": { "status": "not_implemented", "phase": "B", "reason": "…" }    // same
  },
  "upload_formats": ["onnx", "torch_state_dict", "safetensors_state_dict"],
  "upload_max_mb": 512,                       // REDSIM_ML_UPLOAD_MAX_MB, default 512
  "pickle_accepted": false,
  "architectures": ["small_cnn", "smallcnn", "resnet18"],   // loader allowlist, aliases included
  "explainers": { "image": "shap", "tabular": "shap" },
  "defenses": ["feature_squeezing", "spatial_smoothing", "jpeg_compression",
               "adversarial_training", "defensive_distillation"],   // five ids since wave B1 (the two training rows are catalog entries the verify route cannot admit yet, see Verify)
  "llm_narrative": { "configured": false, "gateway": "pythia", "model": null, "persona_set": false,
                     "reason": "Pythia credentials and an ML narrative model are required" },
  "worker_ml_extra": false,                   // what THIS process can import; the worker image is where the extra lives
  "sandbox_enabled": true,                    // the ML sandbox has no off switch (spec 9.4)
  "endpoint_connector": { "status": "not_implemented", "reason": "black-box model endpoints are Phase B", "phase": "B" },   // contract, egress policy, target and broker are on main; registration is wave B2
  "bundled_models": [ { "id": "vehicles_cnn", "name": "…", "modality": "image", "status": "available" } ]
}
```

`llm_narrative.configured` is `true` only when `PYTHIA_BASE_URL`,
`PYTHIA_API_KEY` and `REDSIM_ML_LLM_MODEL` are all set in the API process
environment. The roster is honest about the Phase B state: `text`,
`detection` and `endpoint_connector` stay `not_implemented` until wave B2
(`admission-phase-b`, `endpoint-admission`) admits them, although the
library behind each is on `main` since wave B1. Wave B2 also adds the
`EXPLAINER_ROSTER` block of `redsim/ml/explain/base.py` (explainer per
modality, the black-box `k` cap of 8, the endpoint query caps) and the
`endpoint_connector` contract summary of
[the contract page](endpoint-contract.md). `503 ml_catalog_unavailable` when a registry cannot be imported in
the API process (the API never carries torch, ART or ONNX, and a broken import
is reported rather than shown as an empty list).

## Attack catalog

### `GET /v1/attacks?modality=<image|tabular|text|detection>`

Every registered `AttackAdapter` as its `AttackInfo` row: `id`, `name`,
`domain`, `family` (`evasion` or `control`), `phase`, `access`,
`requires_gradients`, `status` with `reason`, and `params_schema` (bounded
`ParamSpec` entries). **Authenticated.** `modality` filters on `domain`.

On `main` the registry holds ten adapters since wave B1 (`ATTACKS.ids()`,
verified from the tree):

| id | `domain` | `family` | `phase` | `access` | norms declared or derived | Notes |
|---|---|---|---|---|---|---|
| `fgsm` | image | evasion | A | white-box | `linf` | |
| `pgd` | image | evasion | A | white-box | `linf`, `l2` | tabular surrogate-transfer path |
| `hopskipjump` | tabular | evasion | A | black-box | `linf`, `l2` | since B1 also tagged `modality:image` with `IMAGE_DEFAULTS` (`max_iter` 10, `max_eval` 250, `init_eval` 50, `init_size` 50) applied to omitted keys; `decision_based` |
| `noise_control` | image | control | A | black-box | `linf`, `l2` | the benign control |
| `cw_l2` | image | evasion | B | white-box | `l2` | Carlini-Wagner L2, `takes_eps=False`, achieved L2 thresholded against the grid (spec 15.1) |
| `deepfool` | image | evasion | B | white-box | `l2` | `takes_eps=False`, same thresholding |
| `zoo` | tabular | evasion | B | black-box | `linf`, `l2` | score-based, query-counted, frozen features re-imposed |
| `word_substitution` | text | evasion | B | black-box | `edit` | TextFooler-style greedy synonym substitution with a WordNet or JSON lexicon, query-counted; its control `text_noise_control` is run by the text runner and is not a catalog row |
| `dpatch` | detection | evasion | B | white-box | `patch_area` | ART DPatch, `eps` is the patch area share |
| `patch_noise_control` | detection | control | B | black-box | `patch_area` | uniform-noise patch of the same side at the same seeded locations, no model access |

Every row carries `status: available` in the registry; `adv_patch`
(MODALITIES-32) is recorded as not built and is no row. The norms are the
adapter's `norms` attribute or, since B1, derived by
`redsim.ml.attacks.attack_norms` (text and detection adapters get their
modality's norm, an adapter with a `norm_l2` parameter gets `linf` and `l2`,
anything else `linf`) and exposed as `norm:<n>` capability tags next to
`modality:<m>`, `black_box`, `white_box`, `query_counted`, `score_based`,
`decision_based`. `modality` filters on `AttackInfo.domain` today, so
`?modality=image` does not list `hopskipjump` even though it carries the
`modality:image` tag; wave B2 switches the filter to the tag and adds
additive `capabilities` and `domains` keys to each row. Campaign admission
on `text` and `detection` targets, and the `edit` and `patch_area` norms on
`POST /v1/models/{id}/attacks`, are wave B2 as well (see
[Start a campaign](#start-a-campaign)). `503 ml_catalog_unavailable` on an
import failure.

Since `c3868e5` the route also loads the opt-in third-party adapters of the
`redsim.ml.attacks` entry-point group once per API process (only when
`REDSIM_PLUGINS=1`, through `redsim.plugins.load_ml_attack_plugins` with the
`REDSIM_PLUGINS_ALLOW` allowlist, the `AttackAdapter` conformance check and
the Ed25519 signature gate) before listing, and reports the discovery rows
under `plugins` so a rejected or skipped plugin is visible rather than
silently absent. A plugin whose id is already registered is `rejected`, never
substituted.

```jsonc
{
  "attacks": [ { "id": "fgsm", "domain": "image", "family": "evasion", "requires_gradients": true, "status": "available", "params_schema": [ "…" ] } ],
  "count": 10,
  "plugins": { "enabled": false }          // REDSIM_PLUGINS unset: nothing is scanned or imported
}
```

With the gate on, `plugins` is `{"enabled": true, "rows": [...]}` and each
row is a `PluginInfo` dict: `name`, `kind: "attack"`, `group:
"redsim.ml.attacks"`, `distribution`, `version`, `status` (`loaded`,
`rejected` or `skipped`), `detail` (the reason for a rejected or skipped row,
empty for a loaded one) and `signature` (the verifying key id when signature
enforcement is on and verified, else `null`). A failure of the loader itself
(keyring, entry-point metadata) is `503 ml_plugins_unavailable` with
`reason`, not cached, so the next request retries. Per-plugin failures never
raise. One caveat is recorded in the route's docstring: when
`redsim.scanners` was imported earlier in the same process with the gate on,
its import already registered the group and the rows here read
`rejected: already registered` while the adapters are listed in the catalog.

## Dataset catalog

### `GET /v1/datasets`

The bundled evaluation datasets as `redsim ml build-assets` recorded them in
`assets/MANIFEST.json` (`REDSIM_ML_ASSETS_DIR`, default `./assets`).
**Authenticated.** When no manifest is built the response says so instead of
presenting an empty list as a healthy catalog.

```jsonc
{
  "datasets": [
    { "id": "military_vehicles", "name": "…", "license": "MIT", "source_url": "…", "classes": ["…"],
      "size": 9444, "format": "…", "revision": "<sha>", "role": "demo", "fixture_only": false,
      "reachability": "bundled", "bundled_splits": ["test_coarse"], "compatible_modalities": ["image"] }
  ],
  "count": 3,
  "assets": { "status": "built", "assets_dir": "/…/assets", "built_at": "…" }   // or {"status": "missing", "reason": "…"}
}
```

`role` is `ci_fixture` for fixture-only entries (the CIFAR-10 slice), which
are listed honestly and never used as demo evidence.

## Defense catalog

### `GET /v1/defenses`

The defense catalog (`redsim.ml.defenses.list_defenses()`). **Authenticated.**

| id | `kind` | ART class or implementation | modalities | Catalog `phase` |
|---|---|---|---|---|
| `feature_squeezing` | preprocessing | `art.defences.preprocessor.FeatureSqueezing` | image, tabular | A |
| `spatial_smoothing` | preprocessing | `art.defences.preprocessor.SpatialSmoothing` | image | A |
| `jpeg_compression` | preprocessing | `art.defences.preprocessor.JpegCompression` | image | A |
| `adversarial_training` | training | `art.defences.trainer.AdversarialTrainer` over a `PyTorchClassifier`, PGD or FGSM at the campaign's reference eps (`redsim.ml.harden.adversarial_training`) | image | B |
| `defensive_distillation` | training | native torch distillation with a temperature (`redsim.ml.harden.distillation`); ART's `DefensiveDistillation` is the cited reference and is not called | image | B |

Rows carry `id`, `name`, `description`, `kind`, `art_class`, `params_schema`,
`modalities`, `references`, `phase`, `status`. Two things to know on `main`
at the wave B1 push:

- The two training rows exist since wave B1 (`hardening` track) with bounded
  params (`epochs` 1 to 5, `train_n` 32 to 2000, `batch_size`, `lr`,
  `backbone_frozen` default true, `wall_budget_s` 1 to 600; `eps` 0 meaning
  the campaign's reference eps and `pgd_iters` 0 meaning FGSM for
  adversarial training; `temperature` 1 to 40 for distillation) and their
  trainers run inside the sandbox child. **The verify route cannot admit them
  yet**: `POST /v1/findings/{id}/verify` resolves against the preprocessing
  set `DEFENSES` and answers `501 not_implemented` (`phase: "B"`) for a
  training id until wave B2 `admission-phase-b` switches to `ALL_DEFENSES`
  (see [Verify](#verify)).
- The route stamps `phase: "A"` and `status: "available"` on every row it
  returns, the training rows included, while their catalog entries say
  `phase: "B"`. Read `kind` to tell them apart until wave B2 makes the route
  pass the catalog's `phase` through.

`503 ml_catalog_unavailable` on an import failure.

## Models

Model targets are `Target` rows of kind `ml_model_artifact` (or
`ml_model_endpoint`, Phase B) whose `detail` JSONB holds the
`MLModelManifest`, the `status` (`registered`, `validating`, `available`,
`refused`, or `deleted` after a soft delete), the blob reference and the
validation report. Bundled registrations are per project: the `Target` id is
`<bundled_id>-<8 hex>` and `Target.value` is `bundled:<bundled_id>`.

### `GET /v1/models?project=<id>`

**Membership.** The project's live registered targets (soft-deleted rows are
hidden), followed by the bundled catalog entries not yet registered in that
project (fixture-only entries such as `cifar10_smallcnn` are never listed), and
the LLM domain as one `not_implemented` row with its reason.

```jsonc
{
  "models": [
    { "id": "vehicles_cnn-3fa9c2d1", "project_id": "default", "registered": true, "bundled_id": "vehicles_cnn",
      "name": "…", "source": "bundled", "modality": "image", "format": "torch_state_dict", "sha256": "…",
      "manifest": { "…": "MLModelManifest" }, "status": "available", "refusal_reason": null, "reason": null,
      "validation": { "detected_format": "torch_state_dict", "input_shape": [3, 128, 128], "class_count": 7,
                      "gradients": true, "onnx_torch_argmax_agreement": null, "source": "asset_manifest" },
      "last_run_id": "run-…" },
    { "id": "url_trees", "registered": false, "bundled_id": "url_trees", "source": "bundled", "modality": "tabular",
      "status": "available", "…": "catalog entry, not yet registered here" },
    { "id": "…", "registered": false, "source": "endpoint", "modality": "llm", "status": "not_implemented", "phase": "B", "reason": "…" }
  ],
  "count": 3
}
```

`503 ml_catalog_unavailable` when the target registry cannot be imported.

### `GET /v1/models/{model_id}`

**Membership** on the target's project (or on `?project=` for an unregistered
catalog entry). The list row plus `campaign_history` (one entry per run on the
target, newest first) and `last_run_id`. `404 not_found` for unknown ids and
soft-deleted targets.

### Register a model {#register-a-model}

#### `POST /v1/models`

**RBAC: `model.register` (remediator+).** Three sources share the route. The
`model.register` audit row precedes every `Target`, `Run` and `Job` row, and
every refusal writes a `model.register` row with `success=False` before it is
raised.

**Bundled** (`Content-Type: application/json`):

```json
{ "source": "bundled", "project_id": "default", "bundled_id": "vehicles_cnn" }
```

`201` with the model row (`status: "available"`, `campaign_history: []`). The
service verifies the weights and the bound evaluation split against the
manifest digests, copies the weights into the blob store under
`bundled/<bundled_id>/…` and writes the `Target`. Refusals:

| Status | `code` | When |
|---|---|---|
| 404 | `not_found` (`reason: unknown_bundled_model`) | unknown id, or a fixture-only id |
| 409 | `already_registered` (`target_id`, `sha256`) | a live registration of that bundled id already exists in the project |
| 409 | `model_load_refused` (`status: not_implemented`, `refusal_reason: bundled_assets_missing`) | no built assets, no manifest entry, or an invalid manifest |
| 409 | `model_load_refused` (`status: refused`, `refusal_reason: assets_unverified`, `reasons`) | weights or split fail digest verification |
| 503 | `ml_catalog_unavailable` | the target registry cannot be imported |

**Upload** (`multipart/form-data`, fields `file`, `declared_format`,
`modality`, `architecture_id`, `license_statement`, `dataset_id`,
`dataset_split`, `name`):

The API performs the static checks of spec 9.3 only. `Content-Length` is
required (`411`), the cap `REDSIM_ML_UPLOAD_MAX_MB` (default 512) is enforced
before and while the stream is read, the first bytes are sniffed against
`declared_format`, the sha256 is computed, the bytes go to the blob store under
`{project}/models/{target_id}/{safe filename}`, and the `Target`
(`status: "validating"`), its `ml.ingest` `Run` and a `model.validate` `Job` are
written and `redsim.ml_model_validate` is enqueued. Model bytes are never
deserialised in the API process. `201`:

```jsonc
{ "id": "<32 hex>", "status": "validating", "source": "upload", "format": "onnx", "sha256": "…",
  "ingest_run_id": "run-…", "ingest_job_id": "job-…", "enqueued": true, "campaign_history": [], "…": "…" }
```

| Status | `code` | When |
|---|---|---|
| 411 | (plain string) | no `Content-Length` |
| 413 | `model_too_large` | `Content-Length` or the streamed size exceeds the cap |
| 415 | `pickle_refused` | `.pkl`, `.pickle`, `.joblib`, `.sav`, `.dill`, or a pickle opcode as the first byte. No override in Phase A |
| 415 | `unsupported_model_format` | unknown `declared_format`, empty file, magic bytes match no accepted format, or `detected_format` differs from the declaration |
| 422 | `architecture_required` | `torch_state_dict` or `safetensors_state_dict` without `architecture_id` |
| 422 | `architecture_not_allowlisted` (`allowed`) | `architecture_id` outside the loader catalog |
| 422 | `dataset_incompatible` (`field`) | `dataset_id` or `dataset_split` cannot be bound to a bundled evaluation split of the right modality |
| 422 | `license_required` | empty `license_statement` (spec 11.1: no license statement, no registration) |
| 501 | `not_implemented` (`phase: "B"`, `field: modality`) | a modality other than `image` or `tabular`. `text` and `detection` uploads (`sklearn_joblib` text pipelines, detector `state_dict`s) are wave B2 `admission-phase-b` / `endpoint-admission`; the bundled `sms_tfidf_lr` and `assets_frcnn_mnv3` are built by `redsim ml build-assets --dataset text` / `--dataset detection` and registered through `source: bundled` |

Deep validation (load inside the sandbox child, shape and class-count check,
ONNX to torch conversion and argmax agreement) happens in the worker and moves
`status` to `available` or `refused` with a `refusal_reason` from the frozen
vocabulary (`pickle_refused`, `unsupported_format`, `architecture_missing`,
`load_failed`, `shape_mismatch`, `size_limit`, `timeout`). A refused upload has
its blob deleted.

**Endpoint** (`source: "endpoint"`): **Phase B, 501 until built**
(`501 not_implemented` with `phase: "B"`). The library it will call is on
`main`: `EndpointRegistration` and the `endpoint-v1` request and response
contract (`redsim/ml/targets/endpoint_contract.py`, wave B0), the egress
policy (`redsim/ml/endpoint_egress.py`, wave B0), `MLModelManifest.endpoint`
(wave B0) and the `EndpointTarget`, worker-parent `PredictBroker` and
`probe_endpoint_sandboxed` (wave B1). Wave B2 `endpoint-admission` replaces
the 501 with: body validation through `EndpointRegistration` (modality
`image` or `tabular`, `input_shape`, `class_names` or `n_classes`,
`batch_rows` 1 to 1024, `timeout_s` up to 60, the required
`evaluation_instance_attestation: true`, a `bearer` or `header`
`AuthProfile`), the static egress check (`422 endpoint_url_invalid`,
`403 endpoint_not_allowlisted`, `403 egress_refused`,
`422 auth_profile_kind_unsupported`), the `model.register` audit row with
`allowlist_check`, a `Target` of kind `ml_model_endpoint` whose manifest has
`format: "endpoint"`, `gradients: false` and the descriptor digest as
`sha256`, and validation through the broker (`endpoint_unreachable`,
`endpoint_schema_mismatch` become `refusal_reason` `load_failed` /
`shape_mismatch`). Registration is admin (`target.manage`), not
`model.register`. Everything the endpoint has to speak is on
[the contract page](endpoint-contract.md).

### Delete a model {#delete-a-model}

#### `DELETE /v1/models/{model_id}`

**RBAC: `target.manage` (admin).** A soft delete: the `target.manage` audit row
(`op: delete`) is written first, then `detail.status` becomes `deleted` with
`deleted_at` and `deleted_by`. Runs, findings, artifacts, `ml_campaigns` and
audit rows are retained. The upload blob is removed unless another live target
shares the same bytes, and bundled assets are never deleted here.

```json
{ "deleted": "vehicles_cnn-3fa9c2d1", "status": "deleted", "blob_deleted": null }
```

`blob_deleted` is `true`, `false` (shared) or `null` (bundled). `404 not_found`
for unknown or already deleted targets, `409 campaign_in_flight` while a run on
the model is queued or running.

## Campaigns

### Start a campaign {#start-a-campaign}

#### `POST /v1/models/{model_id}/attacks`

**RBAC: `attack.run` (scanner+)** on the model's project. Admits one campaign
as one `attack.run` job on `redsim.ml_campaign_run` (see
[orchestration](../architecture/ml-vertical.md#orchestration)). The
`attack.run` audit row precedes every row and the enqueue, and every refusal
writes a `success=False` `attack.run` row.

```jsonc
{
  "attack_ids": ["fgsm", "pgd"],            // required, non-empty, registry ids
  "norm": "linf",                           // linf (default) | l2
  "eps_grid": [0.01, 0.03, 0.1],            // default per norm: linf (0.01, 0.03, 0.1), l2 (0.25, 0.5, 1.0); at most 3 members
  "reference_eps": 0.03,                    // must be a grid member; default 0.03 for the default L-inf grid
  "n_samples": 200,                         // 10 to 1000
  "seed": 0,
  "include_control": true,
  "explain_k": 8,                           // 0 to 32
  "auto_recommend": true,
  "llm_narrative": false,                   // opt in; needs Pythia configured on the worker
  "attack_params": { "pgd": { "max_iter": 20 } },   // per attack; eps and the norm are grid-owned, never set here
  "dataset_id": "military_vehicles",        // defaults to the dataset the model manifest binds
  "modality": "image",                      // defaults to the model's modality
  "parent_run_id": null                     // rerun of a failed or cancelled campaign with the parent's configuration
}
```

`202` JobHandle. The `Run` has `scanner = "ml.campaign"`, the `Job` type
`attack.run`, and the `ml_campaigns` row `kind = "attack"` with the frozen
config and its `settings_hash`. Server-owned keys (`target_snapshot`,
`attacks`, `defense`, `scoring`) in the body are ignored.

| Status | `code` | When |
|---|---|---|
| 404 | `not_found` | unknown target, another project, or not an ML kind |
| 501 | `not_implemented` (`phase: "B"`) | an `ml_model_endpoint` target, a non Phase A modality (`text`, `detection`), or an attack whose `status` is not `available`. Wave B2 `admission-phase-b` replaces this with `SUPPORTED_MODALITIES` over all four modalities, per-modality default grids (`edit` {0.1, 0.2, 0.3} with reference 0.2, `patch_area` {0.01, 0.03, 0.05} with reference 0.03), a `422 params_out_of_range` (`field: norm`) for a norm the adapter does not declare, the adapter's domain defaults applied before `resolve_params`, and `n_samples` caps for the slow adapters (image HopSkipJump 64, `cw_l2` and `zoo` 100). The Phase B adapters `cw_l2`, `deepfool` (image, L2 grid) and `zoo` (tabular) carry `status: available` and are admissible on the Phase A modalities today; an adapter asked to run in a norm it does not declare is recorded `not_run` by the runner rather than refused at admission until the B2 check lands |
| 409 | `model_load_refused` (`status`, `refusal_reason`) | the target's status is not `available` (still validating, refused, deleted, or no status recorded) |
| 422 | `unknown_attack` | an id outside the registry |
| 422 | `attack_modality_mismatch` | campaign modality differs from the model's, or the attack declares no `modality:<modality>` capability tag (`dd2bbd4`: the tags decide, not `AttackInfo.domain`, so `pgd` is admitted on tabular) |
| 422 | `attack_requires_gradients` | a white-box attack on a model whose manifest says `gradients: false`, unless the adapter declares `surrogate_transfer` and the target declares a surrogate (`58461cc`: PGD on `url_trees` then runs by surrogate transfer, spec 12.9) |
| 422 | `eps_grid_invalid` (`reasons`) | not a list, not strictly ascending, outside (0, 1], or more than three members |
| 422 | `reference_eps_not_in_grid` | `reference_eps` given but not a grid member |
| 422 | `params_out_of_range` (`field`) | a bad `norm`, empty `attack_ids`, `attack_params` naming attacks outside `attack_ids`, adapter parameter bounds, or any other `CampaignConfig` validation error |
| 422 | `dataset_incompatible` | `dataset_id` differs from the manifest binding, or neither names one |
| 409 | `campaign_not_terminal` | `parent_run_id` names a run that is still queued or running |
| 503 | `queue_unavailable` | the broker refused the enqueue, and the Run, Job and campaign rows are rolled back |

Two admission details changed in wave 3. Since `dd2bbd4` admission strips
the grid-owned `eps` and `norm_l2` from `attack_params` before validation and
freezes only the caller-supplied keys with the adapter's coerced values
(`{"fgsm": {}}` when nothing was passed), so the runner, which supplies `eps`
from the grid at run time and refuses a config that sets it, accepts every
API-launched config. Adapter defaults are therefore no longer part of
`settings_hash`, and provenance records the effective values. Applicability
is read from the adapter's `modality:<domain>` capability tags rather than
`AttackInfo.domain`, and `58461cc` exempts a `surrogate_transfer` adapter on
a target with a declared surrogate from the gradients check, so the tabular
demo set `["pgd", "hopskipjump"]` on `url_trees` is admitted.

### Campaign record {#campaign-record}

#### `GET /v1/runs/{run_id}/campaign`

**Membership.** The immutable `ml.run_record` artifact of the run (the newest
row when several exist), verified against its recorded sha256, plus three
mutable projections appended to the response: `reviewer_notes`, `project_id`
and `findings` (the run's `Finding` rows in the wire shape of
[Findings](#findings)). Its shape is the frozen `CampaignRecord`
(`tests/ml/fixtures/run_record.json`): config, target, attacks, provenance,
measurements, curve, observations, interpretation, recommendations,
limitations, `stages_done`, `completeness`, and either `score` (`MRIRecord`)
or `score_status`, never both.

| Status | `code` |
|---|---|
| 404 | `campaign_not_found` (no `ml_campaigns` row or no `ml.run_record` artifact, or unreadable bytes) |
| 409 | `campaign_artifact_digest_mismatch` (the record bytes no longer match the recorded digest) |

### Compare {#compare}

#### `GET /v1/runs/{run_id}/compare?with=<run_id>`

**Membership on both runs**, checked before either record is read.
Compatibility is decided variable by variable on the frozen config (every
field except `target_id`, `defense`, `llm_narrative`, `auto_recommend`,
`target_snapshot`, `attacks`) plus `sample_indices_sha256`, and a verify pairing
must also share `model_sha256`. Two modes:

- `mode: "verify_delta"` when one run's `baseline_run_id` is the other:
  `verify_run_id`, `baseline_run_id`, `defense`, `delta_source`
  (`persisted` from the worker's score record, or `computed` by the same
  `redsim.ml.scoring.delta` over the two stored records), `mri_before`,
  `mri_after`, `delta_mri`, `delta_dimensions`, `delta_acc_clean`,
  `delta_families` (per family: before, after, both `n`, delta),
  `changed_variables: ["defense"]`, `unchanged_variables`,
  `ignored_variables`, `caveats`.
- `mode: "side_by_side"` for the same settings on a different model:
  `delta: null` and `scorecards` (two full `MRIRecord`s, each with its
  measurements, curve and limitations), `changed_variables`,
  `unchanged_variables`, `ignored_variables`, `caveats`. Two scorecards, never
  one delta (spec 15.6).

| Status | `code` | When |
|---|---|---|
| 409 | `incompatible_campaigns` (`reasons`: the mismatched variable names) | any compared variable differs, `sample_indices_sha256` missing on either run, or a verify pairing on different models |
| 409 | `score_unavailable` (`reasons`) | either run has no `score`, or its `mri` is `null` (a partial score is never compared on the subscores that exist) |

### Reviewer notes {#reviewer-notes}

#### `PATCH /v1/runs/{run_id}/reviewer-notes`

**RBAC: `finding.annotate` (remediator+).** Body
`{"reviewer_notes": "<string, at most 8192 characters>"}`. Gate order:
membership (404 for an unknown run), role, body validation
(`422 reviewer_notes_invalid` / `reviewer_notes_too_long`), campaign lookup
(`404 campaign_not_found`), then the `finding.annotate` audit row (length and
sha256 only, never the text), then the write to `ml_campaigns.reviewer_notes`.
Returns `{run_id, reviewer_notes}`. Reports re-rendered through
`redsim.report_render` carry the notes under their own heading.

## Findings

### `GET /v1/findings?run=<run>&severity=<sev>&limit=<n>`

List findings for a run (or across the caller's projects when `run` is
omitted). Severity filter is one of `critical|high|medium|low|info`.

```json
{
  "findings": [
    {
      "id": "f-uuid", "run_id": "run-abc123", "project_id": "proj-a",
      "severity": "high", "status": "open", "validation_state": "unverified",
      "source_tool": "redsim.ml/pgd", "dedup_key": "…",
      "schema_blob": { "finding_type": "adversarial_ml", "title": "…", "description": "…", "ml": { "…": "MLFindingDetail" } }
    }
  ],
  "count": 1
}
```

A campaign finding is one per attack whose ASR at `reference_eps` crosses
`finding_asr_threshold`. `schema_blob` is a `RedsimFinding` dump with
`finding_type = "adversarial_ml"`, a rules-generated title and description that
cite measurement ids, `remediation_steps` rendered as
`CANDIDATE (not evaluated): …`, and the `MLFindingDetail` block at
`schema_blob["ml"]` (attack, norm, grid, first-success eps, ASR by eps, the
clean, evasion and control measurement rows, the attack's observations,
interpretation, candidates, limitations, artifact ids, review state, verify
outcome). Severity is derived from first-success eps and ASR, never hand-set.

### `GET /v1/findings/{finding_id}`

One finding (`{finding_id}` is the UUID). **Membership.**

### Finding actions {#finding-actions}

#### `POST /v1/findings/{finding_id}/explain`

**RBAC: `explain.run` (scanner+).** Body `{"explain_k"?: 0..32, "seed"?: int}`.
Admits a follow-up campaign copied from the parent's frozen config with the
requested `explain_k` (default: the parent's, at least 1). The child's
observations and interpretation are merged back into the parent finding's
`schema_blob["ml"]`. `Run.scanner = "ml.explain"`, `Job.type = "explain.run"`.
`202` JobHandle.

#### `POST /v1/findings/{finding_id}/harden`

**RBAC: `harden.recommend` (remediator+).** Body
`{"llm_narrative": false}`. Same follow-up mechanism with
`auto_recommend = true`. The candidate recommendations, and the Pythia
narrative when requested and configured, are merged back into the finding.
`Run.scanner = "ml.harden"`, `Job.type = "harden.recommend"`. `202` JobHandle.

Refusals shared by both: `404` (plain string) for an unknown finding or a
missing parent campaign, `409 campaign_not_terminal` while the parent campaign
is queued or running, `409 job_in_flight` when a job of that type is already
queued or running for the finding, `501 not_implemented` (`phase: "B"`) for a
modality without a Phase A implementation.

#### `PATCH /v1/findings/{finding_id}/status`

**RBAC: `finding.review` (approver+)**, then the independence rule in the
service. Body:

```json
{ "status": "false_positive", "expected_status": "open", "reason": "…" }
```

`false_positive` is the only user-owned transition and only from `open` or
`failed`. The `finding.review` audit row (from, to, reviewer, campaign creator,
reason) is written before the status changes. Refusals after the lookup write
a `success=False` row first. Returns
`{id, status: "false_positive", from_status, validation_state, review}` where
`review` is the `FindingReview` block also stored at `schema_blob["ml"].review`.

| Status | When |
|---|---|
| 403 (plain string) | the reviewer is the campaign creator, or a system principal |
| 409 `run_terminal` (`status`, `expected_status` or `allowed_from`) | `expected_status` is stale, or the finding is not `open` or `failed` |
| 422 | empty `reason` |
| 404 | unknown finding |

## Verify

### `POST /v1/findings/{finding_id}/verify`

**RBAC: `verify.replay` (remediator+).** Two admissions share the route. A
finding that carries `schema_blob["ml"]` runs the verify-after-harden loop
through `services.ml_campaigns.create_verify_campaign`. Any other finding takes
the retained replay path unchanged (`200`).

```jsonc
{
  "defense": "feature_squeezing",     // id from GET /v1/defenses; default when omitted, see below
  "params": {},                       // defense parameters, bounded by its params_schema
  "recommendation_id": "r.…"          // optional: the candidate whose defense is measured
}
```

Defense resolution: an explicit `defense` must be a catalog id and, when a
recommendation is named, one that recommendation cites. Omitted with a
recommendation, the sole runnable defense the recommendation cites is used
(several need an explicit choice). Omitted without a recommendation,
`feature_squeezing` (the one Phase A preprocessor that applies to image and
tabular targets). The verify campaign copies the baseline's frozen config, sets
`defense`, records `baseline_run_id`, moves the finding to `fixing`, and
answers `202` with a JobHandle. `Run.scanner = "ml.verify"`,
`Job.type = "verify.replay"`, `ml_campaigns.kind = "verify"`.

| Status | `code` | When |
|---|---|---|
| 404 | `not_found` | unknown finding, a finding with no campaign evidence, or a missing baseline record |
| 409 | `campaign_not_terminal` | the baseline campaign has not finished |
| 409 | `job_in_flight` | a `verify.replay` job is already queued or running for the finding |
| 409 | `score_unavailable` | the baseline has no complete score to measure against, or its record bytes fail the digest check |
| 422 | `unknown_defense` | not in the catalog |
| 422 | `defense_modality_mismatch` | the defense does not apply to the model's modality |
| 422 | `params_out_of_range` (`field`, `reasons`) | bad defense parameters, a defense the named recommendation does not cite, or an ambiguous omission |
| 501 | `not_implemented` (`phase: "B"`) | a training defense (`adversarial_training`, `defensive_distillation`). The trainers are on `main` since wave B1 (`redsim.ml.harden.apply.apply_training_defense`, run as the `defense_apply` stage inside the sandbox child, bounded by `epochs`, `train_n` and `wall_budget_s`, backbone frozen by default, deterministic under the seed, the tabular tree ensemble a typed `training_defense_unavailable`), but this route still resolves against the preprocessing set `DEFENSES`. Wave B2 `admission-phase-b` switches it to `ALL_DEFENSES` with `is_training_defense` dispatch, admits training ids for image targets with a torch module and a bundled training slice only, answers `422 defense_modality_mismatch` on tabular with the tree-ensemble reason, and wave B2 `worker-campaign-phase-b` registers the derived model (`derived_model/weights.pt`, `training_report.json`) as a new `Target` with `MLModelManifest.derived_from` lineage |
| 503 | `queue_unavailable` | enqueue failed, rows rolled back and the finding status restored |

The worker attaches the `MeasuredDelta` to the recommendation naming the
defense, maps the outcome onto `findings.validation_state`
(`verified -> poc_passed`, `still_vulnerable -> poc_failed`,
`inconclusive -> inconclusive`) and `findings.status`
(`fixed` / `failed` / `open`), and writes `verify.execute`. A verify whose ΔMRI
cannot be measured (either score partial) still completes with the outcome
projected from the attack measurements and the reason recorded as a limitation.

## Reports

### `GET /v1/runs/{run_id}/report.{ext}`

**Membership on the run's project, then `report.export` (scanner+).** `{ext}` is
`md | json | html`. For a campaign run the newest report `Artifact` row of that
format (kind `report.<ext>`, or the legacy `ml.report_<ext>`) is served after
its bytes are checked against the recorded digest, with `ETag`. Runs without an
artifact row fall back to the blob key `runs/<run>/report.<ext>` and then the
filesystem `output_dir`.

HTML responses carry the strict headers:

```
Content-Security-Policy: default-src 'none'; style-src 'self' 'unsafe-inline'; img-src data:; base-uri 'none'; frame-ancestors 'none'; form-action 'none'
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
X-Frame-Options: DENY
Content-Disposition: inline
```

JSON and Markdown carry nosniff plus
`Content-Disposition: attachment; filename="redsim-<run>-report.<ext>"`.

| Status | Meaning |
|---|---|
| 400 | ext outside `md`, `json`, `html`, `pdf` |
| 403 | no membership, or below `scanner` |
| 404 | run unknown, or `report not yet rendered` |
| 409 `report_artifact_digest_mismatch` | the artifact bytes no longer match their digest |
| 501 `not_implemented` (`phase: "B"`, `field: ext`) | `report.pdf` |

The Markdown report has the six sections of spec 14.8 in order (configuration
and provenance, measurements with the MRI scorecard sub-block and the ΔMRI

## Audit

### `GET /v1/audit/verify?project_id=<id>&run=<run>&all=1`

Walk a chain and confirm every hash links. **RBAC: `audit.verify` (admin)** on
the chain's project. `?run=<id>` verifies `run:<id>` after resolving the run's
project through the membership check (an admin of another project learns
nothing about it), `?project_id=<id>` verifies `project:<id>` (default
`default`), and `?all=1` verifies every chain the caller may verify (every chain
for a system caller, the `system` chain for any admin, and the project and run
chains of the caller's admin projects) and answers `{"chains": [...]}`, the
shape the audit page renders.

```json
{ "chain_id": "run:run-abc", "verified": true, "count": 42, "event_count": 42, "head_hash": "47b1a9…", "broken_at": null, "reason": null }
```

On a broken chain `verified` is `false` and `broken_at` carries the sequence
number. Because every worker event of a campaign shares the run chain, one
call with `?run=` proves the whole trail from `attack.run` to `job.complete`.

The retained platform routes keep FastAPI's plain `{"detail": "..."}` shape:

- `401 { "detail": "authentication required" }`: no bearer and no cookie.
- `403 { "detail": "CSRF token missing or mismatched" }`.

- `429`: rate limit (per-user or per-project token bucket,

- `503`: `REDSIM_DB_URL` missing.

## Phase B routes {#phase-b-routes}

Wave B0 of the [Phase B plan](../plans/12-phase-b-plan.md) (register row
INTEROP-01 and the `route-stubs` track, on `main` at `29db42c`) mounted every
route a later wave builds, so the tree is truthful about its surface from the
first push: nothing is faked, no row, audit event, job or artifact is written,
and each handler runs the lookup, membership and role gates its real handler
will run before it answers. Every row below is still a stub at the wave B1
push: B1 was the library layer and built no route. What replaces them:
wave B2 builds the LLM probe routes (`llm-api`: `POST /v1/models/{id}/probes`
runs a garak probe set through the Pythia gateway in a credential-minimised

params_out_of_range` (`field: project_id`) for a batch or bulk body that names
