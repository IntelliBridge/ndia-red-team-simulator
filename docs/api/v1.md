# HTTP API reference (`/v1/*`)

This page lists every route `redsim.api.app:create_app()` mounts on `main` at
`703f8f6` plus Phase B wave B4 (2026-09-09, the
[Phase B plan](../plans/12-phase-b-plan.md); verified by building the app
from the wave B4 tree and reading its OpenAPI document, the
[route inventory](#route-inventory) below is that document, plus
[`GET /v1/exports`](#exports) added on 2026-09-09 for the web Exports page,
69 operations): 68 HTTP routes under `/v1`, the 37 Phase A routes, the
15 routes wave B2 built (five of the wave B0 stubs replaced by their real
handlers and ten new paths) and the 13 routes wave B3 built in place of
the last B0 stubs (dataset export and consume, ATLAS coverage, the
integrations roster and the Foundry push, batch campaigns, bulk upload and
the capacity view), `GET /v1/models/score-summaries` (#87) and
`GET /v1/llm/models`, which the earlier count of 70 predated, plus `GET /health`, `GET /metrics`, the
non-prod debug view `GET /v1/__settings` and the run-events WebSocket. The
verify paradigm was removed on 2026-09-09 (product owner decision,
[`docs/project-brief.md`](../project-brief.md)): the four verify and defense
routes left the surface: 68 routes and 69 operations under `/v1` remain. No
route answers `501 not_implemented` as a stub any more; the `501` answers
that remain are the documented Phase B non-builds listed under
[Phase B answers](#phase-b-answers). The Phase B table under
[Phase B routes](#phase-b-routes) carries a status per row, every row
"landed" with its wave, and `tests/test_docs_phase_b_consistency.py` compares
that column with the live handlers. Wave B4 changed no path: its fix pass
made the capabilities roster read from the tree, the attacks filter use the
capability tags, `/campaign` carry `batch_id`, the auth-profile delete emit
`409 auth_profile_in_use`, the single-run admissions consult the capacity
service, and added ten codes in a third 17.3 addendum. Wave B1 (the Phase B
library layer) changed no route;
wave B2 (`endpoint-admission`, `admission-phase-b`, `worker-campaign-phase-b`,
`llm-core`, `llm-api`, `review-workflow`, `reports-compare-weights`,
`codes-b2`) built the services, workers and routes over it; wave B3
(`interop-contribute`, `interop-consume`, `atlas-foundry`,
`bulk-service-routes`, `bulk-upload-capacity-cli`) replaced the 14 remaining
stubs with their handlers and added no new path. What each section says about
a wave was read from the routers, services and tests of its commits. The
endpoint predict contract has its own page,
[Endpoint predict contract](endpoint-contract.md); the interoperability
narrative (what leaves, what enters, the rules) is
[Interoperability](../interop.md). The OpenAPI document at
`/docs` (non-prod) is the executable contract. For header semantics see
[`docs/architecture/auth.md`](../architecture/auth.md), for the role matrix
its "RBAC" section, and for the design of the ML surface section 17 of the
[product spec](../superpowers/specs/2026-09-08-adversarial-ml-redteam-spec.md).
Where the tree knowingly departs from the spec, the
[accepted divergences](../architecture/ml-vertical.md#accepted-divergences)
list in the ML vertical page records it.

Every route below requires either an `Authorization: Bearer …` header **or** a
valid `redsim_api_session` cookie, except `/health` and `/metrics`, which are
unauthenticated. Cookie-authenticated mutations additionally require the
`X-Redsim-CSRF` header that matches the `redsim_csrf` cookie (see
[CSRF](../architecture/auth.md#csrf-double-submit-cookie)).

Routes are grouped by RBAC tier. Roles rank `viewer` < `scanner` <
`remediator` < `approver` < `admin` (`redsim/api/policy.py`). `viewer` passes
every membership (read) gate and fails every gated action.

Every enqueueing route answers `202` with the same JobHandle,
`{"run_id": "…", "job_ids": ["…"], "status_url": "/v1/runs/<run_id>"}`, after
its audit row is on the chain and its `Run`, `Job` and (for campaigns)

that shape plus their own keys, listed in their sections). Every ML refusal
carries the spec 17.3 envelope described under
[Error codes](#error-codes-spec-173). Since wave B2 the mutating ML routes
honour the [`Idempotency-Key`](#idempotency-key) header, the wave B3 routes
under `/v1/campaigns`, `/v1/datasets`, `/v1/models/bulk`, `/v1/runs/{id}/dataset`

Liveness probe. Unauthenticated.

```json
{ "status": "ok", "env": "dev", "db_configured": false }
```

`db_configured` is `true` when `REDSIM_DB_URL` is set. `GET /metrics` is the
Prometheus scrape endpoint (it now includes `redsim_ml_campaigns_total` and
`redsim_ml_stage_seconds` alongside the platform counters). `GET /v1/__settings`
is a non-prod debug view of the resolved API settings.

## Attack catalog

### `GET /v1/attacks?modality=<image|tabular|text|detection>`

Every registered `AttackAdapter` as its `AttackInfo` row: `id`, `name`,
`domain`, `family` (`evasion` or `control`), `phase`, `access`,
`requires_gradients`, `status` with `reason`, and `params_schema` (bounded
`ParamSpec` entries). **Authenticated.** `modality` filters on `domain`.
Since wave B3 (`atlas-foundry`) each row also carries the ATLAS block from
`redsim.ml.atlas.attack_atlas_row`: `atlas_technique` (the stamp
`{id, name, atlas_version}`, `null` for a control), `atlas_techniques` (every
attributed technique with its parent) and `atlas_reason` (why this stamp, for
example that ATLAS `v2026.08` has no text- or patch-specific technique so
`word_substitution` and `dpatch` stamp `AML.T0043`), and the response gains
`atlas`, the pinned release citation as strings (release, version, format
version, published and checked dates, the data file and its sha256, the
licence and its sha256, the attribution sentence). The frozen `AttackInfo`
gains no field. The stamp table is in
[Interoperability](../interop.md#atlas-technique-stamping-and-the-coverage-view).

On `main` the registry holds ten adapters since wave B1 (`ATTACKS.ids()`,
verified from the tree):

| id | `domain` | `family` | `phase` | `access` | norms declared or derived | Notes |
|---|---|---|---|---|---|---|
| `fgsm` | image | evasion | A | white-box | `linf` | |
| `pgd` | image | evasion | A | white-box | `linf`, `l2` | tabular surrogate-transfer path |
| `hopskipjump` | tabular | evasion | A | black-box | `linf`, `l2` | since B1 also tagged `modality:image` with `IMAGE_DEFAULTS` (`max_iter` 10, `max_eval` 250, `init_eval` 50, `init_size` 50) applied to omitted keys; `decision_based` |
| `noise_control` | image | control | A | black-box | `linf`, `l2` | the benign control |
| `cw_l2` | image | evasion | B | white-box | `l2` | Carlini-Wagner L2, `takes_eps=False`, achieved L2 thresholded against the grid (spec 15.1) |
| `deepfool` | image | evasion | B | white-box | `l2` | `takes_eps=False`, same thresholding |
| `zoo` | tabular | evasion | B | black-box | `linf`, `l2` | score-based, query-counted, frozen features re-imposed |
| `word_substitution` | text | evasion | B | black-box | `edit` | TextFooler-style greedy synonym substitution with a WordNet or JSON lexicon, query-counted; its control `text_noise_control` is run by the text runner and is not a catalog row |
| `dpatch` | detection | evasion | B | white-box | `patch_area` | ART DPatch, `eps` is the patch area share |
| `patch_noise_control` | detection | control | B | black-box | `patch_area` | uniform-noise patch of the same side at the same seeded locations, no model access |

Every row carries `status: available` in the registry; `adv_patch`
(MODALITIES-32) is recorded as not built and is no row. The norms are the
adapter's `norms` attribute or, since B1, derived by
`redsim.ml.attacks.attack_norms` (text and detection adapters get their
modality's norm, an adapter with a `norm_l2` parameter gets `linf` and `l2`,
anything else `linf`) and exposed as `norm:<n>` capability tags next to
`modality:<m>`, `black_box`, `white_box`, `query_counted`, `score_based`,
`decision_based`. Since wave B4 each row carries the additive `capabilities`
(the tags) and `domains` (every `modality:<m>` tag stripped of its prefix)
keys and `?modality=` filters on those tags, the rule admission applies, so
`?modality=image` lists `cw_l2`, `deepfool`, `fgsm`, `hopskipjump`,
`noise_control` and `pgd`, `?modality=text` lists `word_substitution` and a
row is listed for every modality it can be admitted on. Campaign admission on
`text` and `detection` targets and the `edit` and `patch_area` norms are live
since wave B2 (see [Start a campaign](#start-a-campaign)).
`503 ml_catalog_unavailable` on an import failure.

Since `c3868e5` the route also loads the opt-in third-party adapters of the
`redsim.ml.attacks` entry-point group once per API process (only when
`REDSIM_PLUGINS=1`, through `redsim.plugins.load_ml_attack_plugins` with the
`REDSIM_PLUGINS_ALLOW` allowlist, the `AttackAdapter` conformance check and
the Ed25519 signature gate) before listing, and reports the discovery rows
under `plugins` so a rejected or skipped plugin is visible rather than
silently absent. A plugin whose id is already registered is `rejected`, never
substituted.

```jsonc
  "attacks": [ { "id": "fgsm", "domain": "image", "family": "evasion", "requires_gradients": true, "status": "available", "params_schema": [ "…" ],
                 "atlas_technique": { "id": "AML.T0043", "name": "Craft Adversarial Data", "atlas_version": "…" },   // wave B3
                 "atlas_techniques": [ "…" ], "atlas_reason": "…" } ],
  "count": 10,
  "plugins": { "enabled": false },         // REDSIM_PLUGINS unset: nothing is scanned or imported
  "atlas": { "release": "v2026.08", "version": "…", "format_version": "…", "published": "…", "checked_on": "…",
             "data_file": "…", "data_sha256": "…", "license": "…", "license_sha256": "…", "attribution": "…" }
}
```

With the gate on, `plugins` is `{"enabled": true, "rows": [...]}` and each
row is a `PluginInfo` dict: `name`, `kind: "attack"`, `group:
"redsim.ml.attacks"`, `distribution`, `version`, `status` (`loaded`,
`rejected` or `skipped`), `detail` (the reason for a rejected or skipped row,
empty for a loaded one) and `signature` (the verifying key id when signature
enforcement is on and verified, else `null`). A failure of the loader itself
(keyring, entry-point metadata) is `503 ml_plugins_unavailable` with
`reason`, not cached, so the next request retries. Per-plugin failures never
raise. One caveat is recorded in the route's docstring: when
`redsim.scanners` was imported earlier in the same process with the gate on,
its import already registered the group and the rows here read
`rejected: already registered` while the adapters are listed in the catalog.

## Dataset catalog

### `GET /v1/datasets?project=<id>`

The bundled evaluation datasets as `redsim ml build-assets` recorded them in
`assets/MANIFEST.json` (`REDSIM_ML_ASSETS_DIR`, default `./assets`).
**Authenticated.** When no manifest is built the response says so instead of
presenting an empty list as a healthy catalog. Since wave B3
(`interop-consume`) the list also carries, after the bundled rows, the
consumed slices (`role: consumed`) of the caller's memberships, or of
`?project=` with membership enforced (a system principal sees every
project's), and `consumed_count`; `count` counts both. A consumed row is the
record projection of [`POST /v1/datasets`](#dataset-consume): `id` (`ds-…`),
`project_id`, `name`, `status` (`validating`, `available`, `refused`),
`refusal_reason`, `license`, `modality`, `class_names`, `n_rows` once parsed,
the declared schema, the file names and digests, never bytes or a blob URL.

```jsonc
{
  "datasets": [
    { "id": "military_vehicles", "name": "…", "license": "MIT", "source_url": "…", "classes": ["…"],
      "size": 9444, "format": "…", "revision": "<sha>", "role": "demo", "fixture_only": false,
      "reachability": "bundled", "bundled_splits": ["test_coarse"], "compatible_modalities": ["image"] }
  ],
  "count": 3,
  "assets": { "status": "built", "assets_dir": "/…/assets", "built_at": "…" }   // or {"status": "missing", "reason": "…"}
}
```

`role` is `ci_fixture` for fixture-only entries (the CIFAR-10 slice), which
are listed honestly and never used as demo evidence.

### Consume a dataset (wave B3) {#dataset-consume}

#### `POST /v1/datasets`

**RBAC: `dataset.register` (remediator+).** Multipart only. Register another
team's Parquet evaluation slice, with an optional Croissant manifest, for the
`image` or `tabular` modality. Nothing is parsed in the API process: the
static checks below run on the bytes and the declared schema, then the parse
happens in the sandbox child of the `redsim.ml_dataset_validate` task
(`scans`). Verified from `redsim/api/v1/datasets.py`,
`redsim/services/ml_datasets.py`, `redsim/ml/interop/consume.py`,
`redsim/workers/tasks/dataset_validate.py` and
`tests/ml/test_interop_consume.py`; the narrative is in
[Interoperability](../interop.md#consume-another-teams-evaluation-slice).

Parts and fields: one part named `file` (Parquet; a second Parquet part is
refused in this wave), an optional part named `manifest` (Croissant JSON-LD,
at most 4 MiB), and the form fields `project_id` (or `?project=`), `name`,
`license_statement` (or the manifest's `license`), `modality` (`image` or
`tabular`), `class_names` (a JSON list or a comma list, else the manifest's),
`label_column` (default `label`), for tabular `features` (names or
`{name, min, max}` objects, else the manifest's `recordSet`), for image
`input_shape` (`[C, H, W]`), `dtype` (`uint8`, `float16`, `float32`,
`float64`, `int32` or `int64`), `value_range` (`[min, max]`) and
`image_column` (default `image`), and `public` (`true` or `false`, declared,
not verified). In order: `Content-Length` (`411` when absent; `413
dataset_too_large` over `REDSIM_ML_DATASET_UPLOAD_MAX_MB`, default 256,
audited on the `?project=` chain before the body is read), `project_id`,
membership, the gate, then the body checks. Every refusal writes a
`success=False` `dataset.register` row first (reason, field, counts and
digests, never a URL string or bytes) and persists nothing.

| Status | `code` | When |
|---|---|---|
| 411 | plain `Length Required` | no `Content-Length` |
| 413 | `dataset_too_large` | the declared length is over the cap |
| 415 | `unsupported_dataset_format` | a JSON body; a `file` part that is not Parquet (`PAR1` at both ends), is empty or carries a pickle-shaped name; a `manifest` part that is not a Croissant `Dataset` with a `distribution` list |
| 422 | `params_out_of_range` (`field: project_id`) | no project anywhere |
| 422 | `remote_reference_refused` (the distribution index only) | a `contentUrl` with a scheme, host, slash, backslash or parent segment, or one that names no uploaded part; a Parquet part the manifest does not list |
| 422 | `license_required` | no `license_statement` and no manifest licence |
| 422 | `schema_undeclared` (`field`) | a missing or invalid `modality`, `class_names`, `features`, `input_shape`, `dtype` or `value_range` |
| 501 | `not_implemented` (`phase: "B"`, `field: modality`) | a `text` or `detection` slice: their consumed-slice loaders are not built |
| 503 | `queue_unavailable` is not raised: a broker outage leaves the durable `validating` row and the `201` says `enqueued: false` | |

On success the service writes the `dataset.register` row, the blobs under
`{project}/datasets/{dataset_id}/{safe name}`, the `ml_datasets` row (`status:
validating`, `manifest_sha256` = the revision = the manifest sha256, or the
Parquet digest when no manifest was sent), an `ml.dataset_ingest` `Run` with
no target and a `dataset.validate` `Job`, then enqueues after the commit.
`201`:

```jsonc
{
  "id": "ds-…", "project_id": "…", "name": "…", "role": "consumed", "status": "validating",
  "license": "…", "modality": "tabular", "class_names": ["…"], "n_classes": 2, "n_rows": null,
  "schema": { "modality": "tabular", "class_names": ["…"], "label_column": "label", "features": ["…"], "…": "…" },
  "files": [ { "name": "slice.parquet", "role": "data", "sha256": "…", "size_bytes": 1234, "content_type": "…" } ],
  "revision": "<manifest sha256>", "ingest_run_id": "…", "ingest_job_id": "…", "enqueued": true
}
```

The worker re-hashes the blobs in the parent (a substituted blob is
`artifact_digest_mismatch` with no child spawned), then parses in the
credential-free sandbox child and marks the row `available` or `refused` with
the child's code (`manifest_digest_mismatch`, `dataset_too_large` over
`REDSIM_ML_DATASET_MAX_ROWS`, default 200000, `schema_mismatch`,
`class_names_mismatch`, `parse_failed`, `sandbox_timeout`, `sandbox_killed`),
writes one `dataset.validate` audit row and the report as the
`ml.dataset_validation_report` artifact of the ingest run, then
`job.complete`. `GET /v1/datasets/{ds-…}` (membership on the slice's
project) is the record with `status`, `refusal_reason` and the parse report
counts. The campaign admission (`POST /v1/models/{id}/attacks`) binds an
`available` slice since the B3 reconcile pass: a `dataset_id` matching
`ds-<hex>` must be an `available` slice of the project whose modality matches
the campaign, else `422 dataset_incompatible` (field `dataset_id`,
`dataset_role: consumed`, the reason named); `dataset_revision` defaults to the
slice's manifest digest and the `attack.run` row carries `dataset_id` and
`dataset_role`. Since wave B4 the upload admission binds a consumed slice too
(`check_upload_dataset` falls back to `consumed_upload_binding` for a `ds-…`
id: an `available` slice of the project, split `eval` only, `422
dataset_incompatible` with the slice's status otherwise) and the worker's
target loader reads a slice the worker parent materialised
(`consumed_eval_slice`); the worker parent does not yet write that block, so
a campaign on a consumed-bound model does not run end to end (INTEROP-16
remainder, README open items).

## Models

Model targets are `Target` rows of kind `ml_model_artifact` (bundled and
uploaded) or
`ml_model_endpoint` (black-box predict endpoints and LLM targets, wave B2)
whose `detail` JSONB holds the `MLModelManifest`, the `status` (`registered`,
`validating`, `available`, `refused`, or `deleted` after a soft delete), the
blob reference or the credential-free endpoint block, and the validation
report. Bundled registrations are per project: the `Target` id is
`<bundled_id>-<8 hex>` and `Target.value` is `bundled:<bundled_id>`. An
endpoint target's `Target.value` is the normalised request URL, which no
projection returns.

### `GET /v1/models?project=<id>`

**Membership.** The project's live registered targets (soft-deleted rows are
hidden), followed by the bundled catalog entries not yet registered in that
project (fixture-only entries such as `cifar10_smallcnn` are never listed), and
the LLM domain as one `not_implemented` row with its reason (the registry's
domain row; real LLM targets are per-project rows of kind
`ml_model_endpoint` with `endpoint_kind: llm` and are listed like any other
registered target). Since wave B2 a row of kind `ml_model_endpoint` reads its
`status` from the manifest (`registered`, `validating`, `available`,
`refused`) and carries `gradients: false`, an `endpoint` block (`host[:port]`
only, scheme, `plaintext`, `auth_profile_id`, `auth_kind`,
`contract_version`, `input_format`, `batch_rows`, `timeout_s`,
`fingerprint_sha256`, `fingerprint_label`, `output_kind`, a sanitised probe
summary, the attestation, `verified: false`) and `available_attacks` (the
black-box evasion adapters for its modality: `hopskipjump` for image,
`hopskipjump` and `zoo` for tabular). The URL, the credential and the
ciphertext never appear in any row; the tests scan the body recursively for
secret-shaped keys.

```jsonc
{
  "models": [
    { "id": "vehicles_cnn-3fa9c2d1", "project_id": "default", "registered": true, "bundled_id": "vehicles_cnn",
      "name": "…", "source": "bundled", "modality": "image", "format": "torch_state_dict", "sha256": "…",
      "manifest": { "…": "MLModelManifest" }, "status": "available", "refusal_reason": null, "reason": null,
      "validation": { "detected_format": "torch_state_dict", "input_shape": [3, 128, 128], "class_count": 7,
                      "gradients": true, "onnx_torch_argmax_agreement": null, "source": "asset_manifest" },
      "last_run_id": "run-…" },
    { "id": "url_trees", "registered": false, "bundled_id": "url_trees", "source": "bundled", "modality": "tabular",
      "status": "available", "…": "catalog entry, not yet registered here" },
    { "id": "…", "registered": false, "source": "endpoint", "modality": "llm", "status": "not_implemented", "phase": "B", "reason": "…" }
  ],
  "count": 3
}
```

`503 ml_catalog_unavailable` when the target registry cannot be imported.

### `GET /v1/models/{model_id}`

**Membership** on the target's project (or on `?project=` for an unregistered
catalog entry). The list row plus `campaign_history` (one entry per run on the
target, newest first) and `last_run_id`; an endpoint target also carries
`validation.probe` (wave B2). `404 not_found` for unknown ids and
soft-deleted targets.

### Register a model {#register-a-model}

#### `POST /v1/models`

**RBAC: `model.register` (remediator+) for `source: bundled` and
`source: upload`; `target.manage` (admin) for `source: endpoint`, checked
before any other field is read (wave B2).** Three sources share the route.
The `model.register` audit row precedes every `Target`, `Run` and `Job` row,
and every refusal writes a `model.register` row with `success=False` before
it is raised.

**Bundled** (`Content-Type: application/json`):

```json
{ "source": "bundled", "project_id": "default", "bundled_id": "vehicles_cnn" }
```

`201` with the model row (`status: "available"`, `campaign_history: []`). The
service verifies the weights and the bound evaluation split against the
manifest digests, copies the weights into the blob store under
`bundled/<bundled_id>/…` and writes the `Target`. Refusals:

| Status | `code` | When |
|---|---|---|
| 404 | `not_found` (`reason: unknown_bundled_model`) | unknown id, or a fixture-only id |
| 409 | `already_registered` (`target_id`, `sha256`) | a live registration of that bundled id already exists in the project |
| 409 | `model_load_refused` (`status: not_implemented`, `refusal_reason: bundled_assets_missing`) | no built assets, no manifest entry, or an invalid manifest |
| 409 | `model_load_refused` (`status: refused`, `refusal_reason: assets_unverified`, `reasons`) | weights or split fail digest verification |
| 503 | `ml_catalog_unavailable` | the target registry cannot be imported |

**Upload** (`multipart/form-data`, fields `file`, `declared_format`,
`modality`, `architecture_id`, `license_statement`, `dataset_id`,
`dataset_split`, `name`):

The API performs the static checks of spec 9.3 only. `Content-Length` is
required (`411`), the cap `REDSIM_ML_UPLOAD_MAX_MB` (default 512) is enforced
before and while the stream is read, the first bytes are sniffed against
`declared_format`, the sha256 is computed, the bytes go to the blob store under
`{project}/models/{target_id}/{safe filename}`, and the `Target`
(`status: "validating"`), its `ml.ingest` `Run` and a `model.validate` `Job` are
written and `redsim.ml_model_validate` is enqueued. Model bytes are never
deserialised in the API process. `201`:

```jsonc
{ "id": "<32 hex>", "status": "validating", "source": "upload", "format": "onnx", "sha256": "…",
  "ingest_run_id": "run-…", "ingest_job_id": "job-…", "enqueued": true, "campaign_history": [], "…": "…" }
```

| Status | `code` | When |
|---|---|---|
| 411 | (plain string) | no `Content-Length` |
| 413 | `model_too_large` | `Content-Length` or the streamed size exceeds the cap |
| 415 | `pickle_refused` | `.pkl`, `.pickle`, `.joblib`, `.sav`, `.dill`, or a pickle opcode as the first byte. No override in Phase A |
| 415 | `unsupported_model_format` | unknown `declared_format`, empty file, magic bytes match no accepted format, or `detected_format` differs from the declaration |
| 422 | `architecture_required` | `torch_state_dict` or `safetensors_state_dict` without `architecture_id` |
| 422 | `architecture_not_allowlisted` (`allowed`) | `architecture_id` outside the loader catalog |
| 422 | `dataset_incompatible` (`field`) | `dataset_id` or `dataset_split` cannot be bound to a bundled evaluation split of the right modality |
| 422 | `license_required` | empty `license_statement` (spec 11.1: no license statement, no registration) |
| 501 | `not_implemented` (`phase: "B"`, `field: modality`) | an upload whose modality is not `image` or `tabular`. `text` and `detection` uploads (`sklearn_joblib` text pipelines, detector `state_dict`s) were not built in wave B2 either; the bundled `sms_tfidf_lr` and `assets_frcnn_mnv3` are built by `redsim ml build-assets --dataset text` / `--dataset detection` and registered through `source: bundled`, and campaigns on them are admitted since wave B2 |

Deep validation (load inside the sandbox child, shape and class-count check,
ONNX to torch conversion and argmax agreement) happens in the worker and moves
`status` to `available` or `refused` with a `refusal_reason` from the frozen
vocabulary (`pickle_refused`, `unsupported_format`, `architecture_missing`,
`load_failed`, `shape_mismatch`, `size_limit`, `timeout`). A refused upload has
its blob deleted.

### Register an endpoint {#register-an-endpoint}

**Endpoint** (`source: "endpoint"`, wave B2 `endpoint-admission`, verified
from `redsim/api/v1/models.py`, `redsim/services/ml_models.py`,
`redsim/workers/tasks/ml_model.py` and `tests/ml/test_endpoint_routes.py`).
**RBAC: `target.manage` (admin)**, checked before any field is read. The
default `endpoint_kind` is `predict`; `endpoint_kind: "llm"` hands off to
[LLM target registration](#register-an-llm-target); any other kind is
`501 not_implemented` with `phase`. In order:

1. The body is validated as `EndpointRegistration`
   ([the contract page](endpoint-contract.md): `url`, `auth_profile_id`,
   `modality` `image` or `tabular`, `dataset_id` and `dataset_split`, `name`,
   `license_statement`, `evaluation_instance_attestation: true`,
   `input_shape`, `class_names` and/or `n_classes`, `batch_rows` 1 to 1024,
   `timeout_s` up to 60, `input_format`, `contract_version`); pydantic errors
   are mapped field by field onto codes (below), `field` always named.
2. `reg.check_url(config.target_allowlist)`, the static egress check, then
   the `AuthProfile` by id (a profile of another project or an unknown id is
   `404 not_found` without leaking the tenant; `form` or `cookie` kinds, or
   `header` without `config.header_name`, are `422 auth_profile_kind_unsupported`),
   then the dataset binding (`check_upload_dataset`: fixture-only datasets
   and a declared class list or count that disagrees with the bound split
   are `422 dataset_incompatible`). Nothing is decrypted, resolved or
   connected here.
3. `authorize("model.register", url, allowlist=)` writes the chained row with
   the `allowlist_check` verdict and a detail of host, scheme, `plaintext`,
   the allowlist entry, `auth_profile_id`, `auth_kind`, modality,
   `input_format`, the dataset binding, `n_classes`, `input_shape`, the
   contract, the descriptor sha256, `batch_rows`, `timeout_s`, the
   attestation and the target, run and job ids. Never the URL's userinfo or
   query, never the secret.
4. A `Target` of kind `ml_model_endpoint` (`value` the normalised URL,
   `verified: false`, owner default ENDPOINT-26) whose `detail` carries the
   `MLModelManifest` dump (`format: "endpoint"`, `sha256` the descriptor
   digest, `size_bytes` 0, `gradients: false`, the `EndpointSpec` block,
   `status: validating`), `source`, `endpoint_kind`, the auth profile id and
   kind, `input_format`, scheme, `plaintext`, the attestation record, the
   registration record and a `validation` block; the `ml.ingest` `Run` and
   the `model.validate` `Job` are committed, then `redsim.ml_model_validate`
   is enqueued. A broker failure withdraws the three rows, writes a
   `success=False` `model.register` row (`queue_unavailable`,
   `rolled_back: true`) and answers `503 queue_unavailable`.

`201` with the model row in `status: "validating"`. The worker's endpoint
variant of validate resolves the credential at pickup, hands it only to the
broker, sends one seeded 8-row probe through `probe_endpoint_sandboxed` and
moves the target to `available` (with `gradients: false`, the response
fingerprint labelled "remote model identity, not a weights digest", latency,
HTTP status, `tls_mode`, rows, requests, retries, bytes, resolved addresses
and limits under `validation.probe`) or `refused` with the frozen
`refusal_reason` (`shape_mismatch` for a contract violation; `load_failed`
for `endpoint_unreachable`, `endpoint_auth_failed`, an egress refusal or
`query_budget_exceeded`) and the typed class, code and message beside it.
After a successful probe the child's descriptor digest becomes
`detail.sha256`, and the registration digest is kept at
`validation.registration_descriptor_sha256`. A deleted profile refuses
without probing (`auth_profile_not_found`); a worker without
`REDSIM_AUTH_PROFILES_KEY` fails the job with a `success=False`
`model.validate` row and never probes anonymously.

| Status | `code` | When |
|---|---|---|
| 422 | `endpoint_url_invalid` (`field: url`) | the URL rules of the contract page (an empty body fails here first) |
| 422 | `auth_profile_required` (`field: auth_profile_id`) | no `auth_profile_id` |
| 422 | `license_required` | empty `license_statement`; also the fallback for a missing `evaluation_instance_attestation` (`field: evaluation_instance_attestation`), since `attestation_required` has no 17.3 row yet |
| 422 | `dataset_incompatible` | `dataset_id` or `dataset_split` cannot be bound, a fixture-only dataset, or a class list or count that disagrees with the split |
| 422 | `schema_undeclared` | `input_shape`, `class_names` or `n_classes` missing or inconsistent |
| 422 | `auth_profile_kind_unsupported` | a `form` or `cookie` profile, or `header` without a header name |
| 422 | `params_out_of_range` (`field`) | any other body violation |
| 404 | `not_found` | an unknown `auth_profile_id`, or one from another project |
| 403 | `endpoint_not_allowlisted` (`rule`, `host`, `target`, `allowlist_check: fail`) | host outside `target_allowlist` |
| 403 | `egress_refused` (`rule`, `host`) | a private, loopback, link-local, multicast or reserved address the allowlist does not exempt |
| 501 | `not_implemented` (`phase: "B"`, `field`) | `modality` `text` or `detection`, an `input_format` the contract does not know, or an `endpoint_kind` other than `predict` or `llm` |
| 503 | `queue_unavailable` | the broker refused the enqueue; the rows are withdrawn |

`DELETE /v1/models/{id}` on an endpoint row makes no blob-store call
(`blob_deleted: null`), keeps the row with `status: deleted`, writes the
host and profile id (never the URL) in the audit detail, and still refuses
with `409 campaign_in_flight` while a run on the target is queued or running.
Campaign admission on an endpoint target is under
[Start a campaign](#start-a-campaign).

### Register an LLM target {#register-an-llm-target}

`POST /v1/models` with `{"source": "endpoint", "endpoint_kind": "llm", ...}`
(wave B2 `llm-api`, `redsim/services/ml_llm.py::register_llm_target`,
**`target.manage`**). Fields: `model_id` (a canonical Pythia id,
`<vendor>/<model>` or `pythia/auto`; embedding models refused), `persona`
(required: the Pythia persona the probe key is scoped to), `guardrail_mode`
(`permission_gate_only`, `content_filtered` or `unknown`, required, owner
default LLM-26: it declares what the hit rates measure), `auth_profile_id`
(a `bearer` profile of the project holding the probe key), optional
`gateway_url` (default `PYTHIA_BASE_URL` on the API; required when that is
unset) and optional `name`. The gateway URL goes through
`redsim.ml.endpoint_egress.check_registration_url` (`422 endpoint_url_invalid`,
`403 endpoint_not_allowlisted`), a live target for the same `(model_id,
gateway host, persona)` is `409 already_registered`, then
`authorize("model.register", gateway_url, allowlist)` and a `Target` of kind
`ml_model_endpoint` (`value` the normalised gateway URL, `detail.endpoint_kind`
`llm`, `modality: llm`, `format: endpoint`, `status: available`,
`validation.entitlement: unverified` until the first probe run checks it).
Refusals write their own `success=False` `model.register` row: `model_id`
problems and a missing `persona` or bad `guardrail_mode` are
`422 params_out_of_range` (the register's `model_id_invalid`, `model_not_chat`
and `gateway_url_required` have no 17.3 row), a missing `auth_profile_id` is
`422 auth_profile_required`, a non-bearer profile
`422 auth_profile_kind_unsupported`, an unknown or foreign profile
`404 not_found`. An attack campaign or compare on an LLM target is refused
(D9: probe results never enter an MRI); probes run through
[`POST /v1/models/{id}/probes`](#llm-probes).

### Delete a model {#delete-a-model}

#### `DELETE /v1/models/{model_id}`

**RBAC: `target.manage` (admin).** A soft delete: the `target.manage` audit row
(`op: delete`) is written first, then `detail.status` becomes `deleted` with
`deleted_at` and `deleted_by`. Runs, findings, artifacts, `ml_campaigns` and
audit rows are retained. The upload blob is removed unless another live target
shares the same bytes, and bundled assets are never deleted here.

```json
{ "deleted": "vehicles_cnn-3fa9c2d1", "status": "deleted", "blob_deleted": null }
```

`blob_deleted` is `true`, `false` (shared) or `null` (bundled). `404 not_found`
for unknown or already deleted targets, `409 campaign_in_flight` while a run on
the model is queued or running.

## Campaigns

### Start a campaign {#start-a-campaign}

#### `POST /v1/models/{model_id}/attacks`

**RBAC: `attack.run` (scanner+)** on the model's project. Admits one campaign
as one `attack.run` job on `redsim.ml_campaign_run` (see
[orchestration](../architecture/ml-vertical.md#orchestration)). The
`attack.run` audit row precedes every row and the enqueue, and every refusal
writes a `success=False` `attack.run` row.

```jsonc
{
  "attack_ids": ["fgsm", "pgd"],            // required, non-empty, registry ids
  "norm": "linf",                           // the modality's norms: image and tabular linf (default) | l2, text edit, detection patch_area (wave B2)
  "eps_grid": [0.01, 0.03, 0.1],            // default per norm: linf (0.01, 0.03, 0.1), l2 (0.25, 0.5, 1.0), edit (0.1, 0.2, 0.3), patch_area (0.01, 0.03, 0.05); at most 3 members
  "reference_eps": 0.03,                    // must be a grid member; defaults 0.03 (linf, patch_area), 0.5 (l2), 0.2 (edit)
  "n_samples": 200,                         // 10 to 1000; detection defaults to 50 and is capped at 200 (wave B2)
  "seed": 0,
  "include_control": true,
  "explain_k": 8,                           // 0 to 32
  "auto_recommend": true,
  "llm_narrative": false,                   // opt in; needs Pythia configured on the worker
  "attack_params": { "pgd": { "max_iter": 20 } },   // per attack; eps and the norm are grid-owned, never set here
  "dataset_id": "military_vehicles",        // defaults to the dataset the model manifest binds
  "modality": "image",                      // defaults to the model's modality
  "parent_run_id": null                     // rerun of a failed or cancelled campaign with the parent's configuration
}
```

`202` JobHandle. The `Run` has `scanner = "ml.campaign"`, the `Job` type
`attack.run`, and the `ml_campaigns` row `kind = "attack"` with the frozen
config and its `settings_hash`. Server-owned keys (`target_snapshot`,
`attacks`, `scoring`) in the body are ignored, except that since
wave B2 a client-sent `scoring` key is refused (`422 params_out_of_range`,
`field: scoring`): the scoring block comes from the rerun parent's frozen
block, else the project's `ml_scoring` override
([ML scoring](#ml-scoring)), else `ScoringConfig()`, validated through
`ScoringConfig` without renormalising. The `202` body and the `attack.run`
audit detail carry `scoring_source` (`parent`, `project` or `default`),
`scoring_weights` and `non_default_weights`.

**Phase B admission (wave B2 `admission-phase-b`,
`redsim/services/ml_campaigns.py`, `tests/ml/test_admission_phase_b.py`).**
`SUPPORTED_MODALITIES` maps `image`, `tabular`, `text` and `detection` to a
`ModalitySpec`: the norms it admits (`linf` and `l2` for image and tabular,
`edit` only for text, `patch_area` only for detection), the default grid and
reference per norm, the `n_samples` default and cap, whether a black-box
endpoint may serve it (image and tabular only) and whether an MRI exists
(`mri=False` for detection, owner default MODALITIES-36). `llm` is in
`NOT_IMPLEMENTED_MODALITIES` and answers `501` pointing at the probe route.
Attack applicability is decided by `attack_supports_norm` from the attack
registry: an adapter asked to run in a norm it does not declare is
`422 params_out_of_range` (`field: norm`) naming the adapter's norms and the
evasion attacks that take the campaign norm on that modality, and the
adapter's domain defaults (`apply_domain_defaults`, for example image
HopSkipJump's `IMAGE_DEFAULTS`) are applied for validation only, so only the
caller's keys are frozen into `attack_params`. The `attack.run` audit detail
carries `modality`, `budget` (the axis label per norm), `target_kind` and, for
an endpoint, a host-only `endpoint` block.

**Endpoint targets.** An `ml_model_endpoint` target is admitted when its
detail carries `url_host` and its `status` is `available`; `gradients` are
forced `false` and no surrogate is honoured, so every white-box attack is
`422 attack_requires_gradients`; endpoints serve `image` and `tabular` only
(`text` and `detection` are `501` with the reason); `explain_k` is capped at
`EXPLAIN_QUERY_CAPS.explain_k` (8, the request recorded); and the worst-case
query budget (clean rows, control rows, HopSkipJump
`n * (init_size + max_iter * (max_eval + 1))` or ZOO
`n * max_iter * binary_search_steps * 2 * nb_parallel` from the resolved
params, times the grid size for attacks that take eps, plus the kernel or
partition explain bound at the caps) is compared with
`EndpointLimits.from_env(modality)` merged with the binding limits and
refused with `429 query_budget_exceeded` carrying `estimate` and `cap`; an
attack without a bound is refused the same way. The frozen config's
`target_snapshot` becomes `endpoint:<host>` with the URL, auth, token and
allowlist keys scrubbed, and its `endpoint` slot records `limits`,
`explain_caps`, `explain_k_requested` and `query_budget`. The worker then
resolves the credential at run time, starts the broker in the parent and
records the broker tally on the record and the audit rows ([ML
vertical](../architecture/ml-vertical.md#endpoint-campaigns-wave-b2)).

| Status | `code` | When |
|---|---|---|
| 404 | `not_found` | unknown target, another project, or not an ML kind |
| 501 | `not_implemented` (`phase: "B"`, `field`, `reason`) | the `llm` modality (probe runs have their own route), an endpoint target without `url_host` in its detail, `text` or `detection` on an endpoint target, or an attack whose `status` is not `available` |
| 409 | `model_load_refused` (`status`, `refusal_reason`) | the target's status is not `available` (still validating, refused, deleted, or no status recorded) |
| 409 | `llm_target_required` | the target is an LLM target (probe results never enter an MRI, D9) |
| 422 | `unknown_attack` | an id outside the registry |
| 422 | `attack_modality_mismatch` | campaign modality differs from the model's, or the attack declares no `modality:<modality>` capability tag (`dd2bbd4`: the tags decide, not `AttackInfo.domain`, so `pgd` is admitted on tabular) |
| 422 | `attack_requires_gradients` | a white-box attack on a model whose manifest says `gradients: false` (every endpoint target), unless the adapter declares `surrogate_transfer` and the target declares a surrogate (`58461cc`: PGD on `url_trees` then runs by surrogate transfer, spec 12.9) |
| 422 | `eps_grid_invalid` (`reasons`) | not a list, not strictly ascending, outside (0, 1], or more than three members |
| 422 | `reference_eps_not_in_grid` | `reference_eps` given but not a grid member |
| 422 | `params_out_of_range` (`field`, `reasons`) | a norm the modality does not admit or the adapter does not declare (`field: norm`), `n_samples` above the modality cap (`field: n_samples`, `cap`), a client-sent or invalid `scoring` block, empty `attack_ids`, `attack_params` naming attacks outside `attack_ids`, adapter parameter bounds, or any other `CampaignConfig` validation error |
| 422 | `dataset_incompatible` | `dataset_id` differs from the manifest binding, or neither names one |
| 429 | `query_budget_exceeded` (`estimate`, `cap`) | an endpoint campaign whose worst-case query estimate exceeds `REDSIM_ML_ENDPOINT_MAX_ROWS` (wave B2) |
| 409 | `campaign_not_terminal` | `parent_run_id` names a run that is still queued or running |
| 503 | `queue_unavailable` | the broker refused the enqueue, and the Run, Job and campaign rows are rolled back |

Two admission details changed in wave 3. Since `dd2bbd4` admission strips
the grid-owned `eps` and `norm_l2` from `attack_params` before validation and
freezes only the caller-supplied keys with the adapter's coerced values
(`{"fgsm": {}}` when nothing was passed), so the runner, which supplies `eps`
from the grid at run time and refuses a config that sets it, accepts every
API-launched config. Adapter defaults are therefore no longer part of
`settings_hash`, and provenance records the effective values. Applicability
is read from the adapter's `modality:<domain>` capability tags rather than
`AttackInfo.domain`, and `58461cc` exempts a `surrogate_transfer` adapter on
a target with a declared surrogate from the gradients check, so the tabular
demo set `["pgd", "hopskipjump"]` on `url_trees` is admitted.

### Campaign record {#campaign-record}

#### `GET /v1/runs/{run_id}/campaign`

**Membership.** The immutable `ml.run_record` artifact of the run (the newest
row when several exist), verified against its recorded sha256, plus the
mutable projections appended to the response: `reviewer_notes`, `project_id`,
`findings` (the run's `Finding` rows in the wire shape of
[Findings](#findings)), `weights` and `non_default_weights` (wave B2) and,
since wave B4, `batch_id` overlaid from the `ml_campaigns` row (`null` for a
single-run admission; owner default BULK-02, no schema change). Its shape is the frozen `CampaignRecord`
(`tests/ml/fixtures/run_record.json`): config, target, attacks, provenance,
measurements, curve, observations, interpretation, recommendations,
limitations, `stages_done`, `completeness`, and either `score` (`MRIRecord`)
or `score_status`, never both.

| Status | `code` |
|---|---|
| 404 | `campaign_not_found` (no `ml_campaigns` row or no `ml.run_record` artifact, or unreadable bytes) |
| 409 | `campaign_artifact_digest_mismatch` (the record bytes no longer match the recorded digest) |

### Compare {#compare}

#### `GET /v1/runs/{run_id}/compare?with=<run_id>`

**Membership on both runs**, checked before either record is read.
Compatibility is decided variable by variable on the frozen config (every
field except `target_id`, `llm_narrative`, `auto_recommend`,
`target_snapshot`, `attacks`) plus `sample_indices_sha256`. One mode:

- `mode: "side_by_side"` for the same settings on a different model:
  `scorecards` (two full `MRIRecord`s, each with its measurements, curve and
  limitations), `changed_variables`, `unchanged_variables`,
  `ignored_variables`, `caveats`. Two scorecards, never a difference between
  them (spec 15.6). The response carries no `delta*` key and
  `changed_variables` names config variables only.

| Status | `code` | When |
|---|---|---|
| 409 | `incompatible_campaigns` (`reasons`: the mismatched variable names) | any compared variable differs, or `sample_indices_sha256` is missing on either run; since wave B2 the scoring block is compared per sub-key, so a differing vector is named `scoring.weights` |
| 409 | `score_unavailable` (`reasons`) | either run has no `score`, or its `mri` is `null` (a partial score is never compared on the subscores that exist) |
| 409 | `llm_target_required` | either run is an LLM probe run (wave B2; the scorecard is at `/v1/runs/{id}/llm-scorecard`) |

Since wave B2 the compare response and `/campaign` carry
`non_default_weights` (and `/campaign` the `weights` vector).

#### `GET /v1/runs/compare?ids=<a>,<b>,<c>` {#compare-many}

**Membership on every run**, checked before any record is read (wave B2
`reports-compare-weights`, `redsim/api/v1/compare.py` over the pure
`redsim/ml/compare.py::comparison_table`; the route is declared before the
`/runs/{run_id}` routes). Between 2 and 10 ids, no repeats
(`422 params_out_of_range`, `field: ids`). Every record must pass its digest
check and carry a complete score. The response is a table in request order
and nothing else: one row per run with `mri`, `grade`, `reading`,
`subscores`, `per_attack`, `inputs`, `weights`, `families` (every
denominator), `curve`, `limitations`, `non_default_weights`, plus
`changed_variables_per_row` (against the first row), `unchanged_variables`
(the intersection), `ignored_variables` and `caveats`. No mean, no rank, no
average: `assert_no_aggregate_keys` refuses any such key before the body is
returned (spec 15.6). `409 incompatible_campaigns` with `reasons` and the
per-pair `pairs`, `409 score_unavailable` naming the runs.

### Reviewer notes {#reviewer-notes}

#### `PATCH /v1/runs/{run_id}/reviewer-notes`

**RBAC: `finding.annotate` (remediator+).** Body

membership (404 for an unknown run), role, body validation

## Findings

### `GET /v1/findings?run=<run>&severity=<sev>&status=<s>&review_state=<r>&source_tool=<t>&limit=<n>`

List findings for a run (or across the caller's projects when `run` is
omitted). Severity filter is one of `critical|high|medium|low|info`. Since
wave B2 the route is served by `redsim/api/v1/ml_findings.py` as a superset
of the core route: `status`, `review_state` (`422` on an unknown state; read
from `schema_blob.<ml|llm>.review.state`) and `source_tool` filters, and
every row carries `review_state` and a `review` summary (`state`, `reviewer`,
`at`, `n_history`, `n_revisions`, `revision`). LLM probe findings
(`source_tool` `redsim.ml/llm_probe`) and analyst drafts (`source_tool`
`manual`) share the list.

```json
{
  "findings": [
    {
      "id": "f-uuid", "run_id": "run-abc123", "project_id": "proj-a",
      "severity": "high", "status": "open",
      "source_tool": "redsim.ml/pgd", "dedup_key": "…",
      "schema_blob": { "finding_type": "adversarial_ml", "title": "…", "description": "…", "ml": { "…": "MLFindingDetail" } }
    }
  ],
  "count": 1
}
```

A campaign finding is one per attack whose ASR at `reference_eps` crosses
`finding_asr_threshold`. `schema_blob` is a `RedsimFinding` dump with
`finding_type = "adversarial_ml"`, a rules-generated title and description that
cite measurement ids, `remediation_steps` rendered one line per candidate
and labelled `CANDIDATE`, and the `MLFindingDetail` block at
`schema_blob["ml"]` (attack, norm, grid, first-success eps, ASR by eps, the
clean, evasion and control measurement rows, the attack's observations,
interpretation, candidates, limitations, artifact ids, review state).
Severity is derived from first-success eps and ASR, never hand-set.
`Finding.status` is `open`, `fixed` or `false_positive`, and no response
carries a validation state.

### `GET /v1/findings/{finding_id}`

One finding (`{finding_id}` is the UUID). **Membership.**

### Finding actions {#finding-actions}

#### `POST /v1/findings/{finding_id}/explain`

**RBAC: `explain.run` (scanner+).** Body `{"explain_k"?: 0..32, "seed"?: int}`.
Admits a follow-up campaign copied from the parent's frozen config with the
requested `explain_k` (default: the parent's, at least 1). The child's
observations and interpretation are merged back into the parent finding's
`schema_blob["ml"]`. `Run.scanner = "ml.explain"`, `Job.type = "explain.run"`.
`202` JobHandle.

#### `POST /v1/findings/{finding_id}/harden`

**RBAC: `harden.recommend` (remediator+).** Body
`{"llm_narrative": false}`. Same follow-up mechanism with
`auto_recommend = true`. The candidate recommendations, and the Pythia
narrative when requested and configured, are merged back into the finding.
`Run.scanner = "ml.harden"`, `Job.type = "harden.recommend"`. `202` JobHandle.

Refusals shared by both: `404` (plain string) for an unknown finding or a
missing parent campaign, `409 campaign_not_terminal` while the parent campaign
is queued or running, `409 job_in_flight` when a job of that type is already
queued or running for the finding, `501 not_implemented` (`phase: "B"`) for a
modality without a Phase A implementation.

#### `PATCH /v1/findings/{finding_id}/status`

**RBAC: `finding.review` (approver+)**, then the independence rule in the
service. Body:

```json
{ "status": "false_positive", "expected_status": "open", "reason": "…" }
```

`status: false_positive` is the dismissal (from `open` only) and
`status: open` the reopen (from `false_positive`); since wave B2 the body may
name a `decision` instead (`422` when neither is given or they disagree) and
an optional `expected_review_state`. The Phase A rules and codes are kept
byte for byte: the `finding.review` audit row (from, to, reviewer, campaign
creator, reason) is written before the status changes, refusals after the
lookup write a `success=False` row first, and the response is
`{id, status, from_status, review}` where `review` is the
`FindingReview` block also stored at `schema_blob["ml"].review` (history is
appended, never replaced, since B2).

| Status | When |
|---|---|
| 403 (plain string) | the reviewer is the campaign creator, or a system principal |
| 409 `run_terminal` (`status`, `expected_status` or `allowed_from`) | `expected_status` is stale, or the finding is not `open` |
| 422 | empty `reason` |
| 404 | unknown finding |

### Review workflow (wave B2) {#review-workflow}

`redsim/services/finding_review.py` (wave B2 `review-workflow`,
`tests/ml/test_review_workflow.py`) holds one transition table
(`TRANSITIONS`) over the pair (`Finding.status`,
`schema_blob.<ml|llm>.review.state`) with six decisions. No new
`Finding.status` value is invented.

| Decision | From | To | Gate | Notes |
|---|---|---|---|---|
| `submit` | review state `draft` | `in_review` | `finding.author`, the draft's author only | freezes the latest revision with `submitted_at` and a sha256 over its three texts and cited ids |
| `confirm` | `unreviewed` or `in_review` | `confirmed` | `finding.review` | `Finding.status` (`open` or `fixed`) untouched |
| `request_changes` | `in_review` | `draft` | `finding.review` | appends a new editable `FindingRevision` (n+1, same author, texts carried) |
| `dismiss` | `Finding.status` `open` | `false_positive` / review `dismissed` | `finding.review` | the Phase A rules and codes, byte for byte |
| `reopen` | `false_positive` | `open` / `unreviewed` | `finding.review` | history keeps the dismissal |
| `resolve` | review `confirmed` | `resolved`, `Finding.status` `fixed` | `finding.review` | requires `review_state: confirmed` only. A finding in any other review state is `409 resolution_blocked` with `unmet: ["review_state_not_confirmed"]`, `status` and `review_state`. A finding closes by reviewer decision |

Independence is identity, never rank: the campaign creator
(`runs.created_by`), the author of the latest revision and
system principals are refused with `403 reviewer_not_independent` carrying
`relation` (dismiss keeps its Phase A plain-string `forbidden`). Every
decision is a compare-and-set on `expected_status` and the optional
`expected_review_state` under `SELECT ... FOR UPDATE` (a no-op on sqlite):
a stale expectation is `409 review_state_conflict` (dismiss keeps
`run_terminal`). Every decision writes its `finding.review` (or
`finding.author` for `submit`) row through `authorize()` before the write,
with the decision, from and to status and review state, the expectations,
reason, reviewer, author, campaign creator and revision
(plus the unmet list and the independence violations on a refusal). A
finding without a review block (neither `ml` nor `llm`) accepts `dismiss`
and `reopen` only; the rest is `409 review_transition_invalid`.

#### `POST /v1/findings/{finding_id}/review/{transition}` and `POST /v1/findings/{finding_id}/review`

Body `{"reason": "…", "expected_status": "…", "expected_review_state"?: "…"}`
for the path form (`404` for an unknown transition) and the same plus
`"decision"` for the body form (the spec 17.4 shape). Both drive the service
above. Returns the finding's wire shape with `review_state` and the review
summary.

#### Analyst drafts: `POST /v1/findings` and `PATCH /v1/findings/{finding_id}/draft`

**RBAC: `finding.author` (remediator+)** on the run's project.
`POST /v1/findings` (201) takes `run_id`, `attack_id`, `title` (up to 512
characters), `severity` (`critical` to `low`), `observation` (up to 8192
characters), optional `interpretation` and `candidate`, and `evidence_ids`
(1 to 256 measurement or observation ids). The run must be terminal with an
`ml_campaigns` row, the attack must be in its attack set, and every evidence
id must exist in the digest-checked `ml.run_record` (tampered bytes are
`409 score_unavailable` with `artifact_digest_mismatch`). The finding carries
`source_tool: manual`, `confidence: low`, `status: open`, the author-declared
severity labelled as such in the description, `review.state: draft`,
`review.revisions[0]`, the cited rows in its `ml` block,
`scanner_finding_id` `manual.<attack>.<hex>` and `dedup_key`
`manual:<run>:<attack>:<digest16>`; the `finding.author` `op: create` row
(ids, counts, the sha256 of the title and revision, never the text) precedes
the row. `PATCH .../draft` appends a revision (author only, `draft` state
only, evidence re-validated) and rewrites the description, evidence and
remediation steps from it. Since wave B4 a draft's `finding_type` is
`adversarial_ml_manual` (`redsim/schema.py` `FindingType` gained the literal
additively) and its `MLFindingDetail` carries the ATLAS stamp of its attack
like a campaign finding.

## Batch and bulk operations (wave B3) {#batch-and-bulk}

The `bulk-service-routes` and `bulk-upload-capacity-cli` tracks, verified
from `redsim/api/v1/batches.py`, `redsim/services/ml_batches.py`,
`redsim/api/v1/models_bulk.py`, `redsim/services/ml_capacity.py`,
`redsim/workers/tasks/capacity.py`, `redsim/ml/compare.py` and
`tests/ml/test_batches.py`, `tests/ml/test_bulk_upload_capacity.py`. Every
batch and bulk admission reuses the single-run boundary member by member (its
own `attack.run` or `model.register` row before its rows),
adds one row for the batch itself, and never computes an aggregate: no mean
or rank across members, and no MRI number in any batch view. A batch `kind`
is `campaign` or `upload`.

### Batch campaigns {#batch-campaigns}

#### `POST /v1/campaigns/batch`

**RBAC: `batch.run` (scanner+)** on the project. One campaign body applied to
several targets of one project. `project_id` comes from the body, a form or
`?project=` (`422 params_out_of_range` without it; `?project=` also keys the
per-project rate bucket). `Idempotency-Key` is honoured; the batch row stores
`sha256(key)`, never the key.

```jsonc
{
  "project_id": "…",
  "target_ids": ["<target_id>", "<target_id>"],          // 1 to REDSIM_ML_BATCH_MAX_MEMBERS (default 20), one modality
  "campaign": { "attack_ids": ["fgsm", "pgd"], "eps_grid": [0.01, 0.03, 0.1], "…": "…" },   // the POST /v1/models/{id}/attacks body minus target_id; a flat body is accepted too
  "max_parallel": 2                                       // optional: members beyond it are admitted deferred (no broker message)
}
```

Write-free pre-checks first, each refusal a `success=False` `batch.create` row:
`422 params_out_of_range` (`target_ids`, a `campaign.target_id` or
`campaign.parent_run_id`, `max_parallel`), `422 batch_too_large` (`cap`,
`requested`), `404 not_found` naming the ids the project cannot see, `422
batch_modality_mismatch` with `groups` (`{modality: [ids]}`). Then one
`batch.create` row on the project chain (`batch_id`, `kind: campaign`,
`target_ids`, `n_members`, `modality`, `config_hash` = sha256 of the canonical
campaign body, `attack_ids`, `max_parallel`, `max_members`), the `ml_batches`
row (`status: queued`), and one `create_attack_campaign` per member through
the unchanged single-run boundary, `batch_id` stamped on the member's
`ml_campaigns` row, `Run.stage_table` and `Job.detail` (with
`batch_member_index`). Before each member the capacity service is consulted
([Capacity](#capacity)): an over-cap member is admitted deferred, a spent
daily budget is collected as that member's refusal. Per-member `ApiError`s
are collected, never fatal: `refused: [{target_id, code, message, attempted,
…}]`; after a `queue_unavailable` member the rest are recorded as not
attempted; when no member was admitted the batch answers `422
batch_member_refused` with `members` and `batch_id` (the row survives as
`failed` with a closing `success=False` `batch.create` row).

`202`:

```jsonc
{ "batch_id": "…", "kind": "campaign", "project_id": "…", "modality": "image", "status": "queued",
  "status_url": "/v1/campaigns/batch/<batch_id>",
  "members": [ { "target_id": "…", "run_id": "…", "job_ids": ["…"], "status_url": "/v1/runs/<run_id>", "deferred": false } ],
  "run_ids": ["…"], "refused": [], "n_members": 2, "n_refused": 0, "config_hash": "…" }
```

#### `GET /v1/campaigns/batch?project=<id>&limit=<n>`

**Membership** on `?project=` when named, else the caller's accessible
projects. `{batches: [...], count}`.

#### `GET /v1/campaigns/batch/{batch_id}`

**Membership** on the batch's project (`404` unknown). The roll-up view:
the batch fields and the requested block, `refused`, the members in admission
order, each with `status`, `stage`, `stages_done`, job ids and statuses,
`deferred`, `attack_ids`, `settings_hash`, `score_status`
(`scored`, `pending`, `unavailable`) and a `scorecard_url` link to its own
`/campaign`, never an MRI number; `counts`; `state` `active` or `terminal`;
and `status` recomputed from the member run statuses: `queued` (every member
queued), `running` (any member not terminal), `succeeded` (every member
succeeded and nothing refused), `partial` (succeeded members beside failed,
cancelled or refused ones), `failed` (every member failed, or nothing
admitted), `cancelled` (every member cancelled).

#### `GET /v1/campaigns/batch/{batch_id}/compare`

**Membership.** The members' scorecards grouped by comparability through
`redsim.ml.compare.comparability_groups` (the pairwise rule of `/compare` and
the N-run table, greedy in request order): `200` with `mode:
batch_side_by_side` and one group (`key`, `run_ids`, `scorecards` as full
scorecard projections, `changed_variables`, `unchanged_variables`), plus
`unavailable` (queued, running or record-less members with reasons) and
`caveats`; `409 incompatible_campaigns` with `groups`, `pairs`, `reasons` and
`unavailable` when the scored members form several groups; `409
score_unavailable` when no member carries a complete MRI. No mean, rank or
aggregate is computed (`assert_no_aggregate_keys`).

#### `POST /v1/campaigns/batch/{batch_id}/cancel`

**RBAC: `run.cancel` (remediator+).** `409 run_terminal` (a `success=False`
`batch.cancel` row) when every member is terminal; else one `batch.cancel`
row (member ids, `cancelling`, `already_terminal`), then
`services.runs.cancel_run` per live member (each its own `run.cancel` row,
jobs flipped, Celery revoke best effort), `cancelled_at` stamped. `200
{batch_id, status, cancelled, already_terminal, jobs_cancelled}`.

### Bulk upload {#bulk-upload}

#### `POST /v1/models/bulk`

**RBAC: `model.register` (remediator+).** Several model files in one
multipart request: the `files` parts plus one `manifest` JSON part,
`{"project_id": "…", "items": [{"filename", "name", "modality", "dataset_id",
"license_statement", "declared_format", "architecture", "dataset_split"}, …]}`.
In order: `Content-Length` (`411`; `413 bulk_too_large` over
`REDSIM_ML_BULK_UPLOAD_MAX_MB`, default 1024, before the body is parsed),
`project_id` (`422`), membership and the gate, the manifest shape (`422`),
the file-count cap (`422 bulk_too_many_files` over
`REDSIM_ML_BULK_UPLOAD_MAX_FILES`, default 10), a one-to-one match of
`items[].filename` to the parts (`422`), then one `bulk.upload` audit row and
one `ml_batches` row (`kind: upload`), then per file the single-upload
admission unchanged (the spec 9.3 static checks, its own `model.register` row,
a `Target` in `validating`, an `ml.ingest` `Run`, a `model.validate` `Job`,
the enqueue on `redsim.ml_model_validate`, `bulk_id` stamped on all). No model
bytes are deserialised in the API process. A per-file refusal is a result row
(`status: refused`, `code`, `field`, `message`, `http_status`), so the answer
is `201` when every file is validating, `207` when mixed, `422
batch_member_refused` when every file was refused:

```jsonc
{ "bulk_id": "…", "project_id": "…", "kind": "upload", "n_files": 2, "n_admitted": 2, "n_refused": 0,
  "results": [ { "index": 0, "filename": "a.onnx", "status": "validating", "target_id": "…", "ingest_run_id": "…",
                 "ingest_job_id": "…", "sha256": "…", "detected_format": "onnx", "size_bytes": 1234, "enqueued": true } ],
  "status_url": "/v1/ml/capacity?project=<project_id>" }
```

`REDSIM_ML_BULK_UPLOAD_MAX_MB` buffers the whole multipart in the API process;
set it lower (256) on a small Fargate API task.

### Capacity {#capacity}

Per-project capacity (`redsim/services/ml_capacity.py`, ML-import-free):
`Project.ml_max_concurrent_runs` (default
`REDSIM_ML_MAX_CONCURRENT_RUNS_PER_PROJECT`, 2) and
`Project.ml_daily_run_budget` (default `REDSIM_ML_DAILY_RUN_BUDGET`, alias
`REDSIM_ML_PROJECT_DAILY_RUN_BUDGET`; unset is uncapped). Counts come from the
jobs table, never from broker inspection. Over the concurrency cap an
admission is **deferred**, never refused: its `Run` and `Job` rows exist with
`status: queued`, `Job.detail.deferred = true` and no broker message, and the
`202` body carries the `capacity_deferred` marker (a body field, never an
`ApiError`). Over the daily budget the admission is refused `429
daily_budget_exceeded` with `budget`, `used`, `requested`, `resets_at` (UTC
midnight) and `retry_after`, after its `success=False` audit row. Deferred
jobs move on through `dispatch_deferred` (oldest first while a slot is free,
the flag restored on a broker failure) from the beat task
`redsim.ml_dispatch_deferred` every 60 s on `default`, and from the end of
every campaign run: `redsim.ml_campaign_run` enters
`redsim.workers.tasks.capacity.deferred_continuation(job_id)` around its
`task_context`, which calls `continue_deferred` on every exit path (return,
cancel, skip, failure, retry) once the terminal status is committed and never
raises; the beat sweep is the backstop. Since wave B4 the single-run
boundary `create_attack_campaign` calls
`admit_or_defer` before the admission row itself (BULK-20, -21): a spent
budget is `429 daily_budget_exceeded` after its `success=False` row, an
over-cap admission is written deferred and not enqueued and the `202` body
carries `deferred: true` plus the `capacity_deferred` marker under
`capacity`; a body dispatched at once is unchanged. The batch service decides
per member and passes `capacity_check=False`, so each member is decided
exactly once. The gauges `redsim_jobs_active` (now
filled), `redsim_ml_deferred_runs{project}` and
`redsim_ml_daily_budget_used{project}` are set from the dispatcher's sample
(`redsim/observability.py::set_capacity_gauges`).

#### `GET /v1/ml/capacity?project=<id>`

**Membership** on `?project=` when named (`404` for an unknown project), else
every project the caller can read; a system principal also gets a `global`
block. `{projects: [{project_id, max_concurrent_runs, daily_run_budget,
sources {max_concurrent_runs, daily_run_budget}, running_jobs, queued_jobs,
deferred_runs, active_runs, slots_free, used_today, budget_remaining,
resets_at, budget_window}], limits: {max_concurrent_runs_default,
daily_run_budget_default, env, bulk_upload {max_files, max_total_mb,
per_file_max_mb}, batch}, source, project?, global?}`; the counts come from
the jobs table, never from broker inspection, and `budget_window` says that
cancelled runs count against the day's admissions.

```jsonc
{ "integrations": {
    "foundry": { "integration": "foundry", "status": "disabled", "reason": "…",   // disabled | misconfigured (with "rule") | configured (with "tls")
                 "host_configured": false, "target_ref_configured": false, "attested": false,
                 "route": "POST /v1/runs/{run_id}/integrations/foundry", "gate": "integration.push (admin)", "queue": "default",
```

`foundry` is `disabled` while `REDSIM_INTEGRATION_FOUNDRY_URL` is unset (the

#### `POST /v1/runs/{run_id}/integrations/foundry`

**RBAC: `integration.push` (admin)** on the run's project. Body
`{"auth_profile_id": "…", "target_ref": "ri.foundry.main.dataset.…", "payload": "scorecard"}`
(`target_ref` optional when `REDSIM_INTEGRATION_FOUNDRY_DATASET_RID` is set;
extra keys refused). A malformed body is `422 params_out_of_range` naming the
field and never reaches the admission boundary; every refusal after the
lookup is a `success=False` `integration.push` row on the campaign run's
chain (ids, code, host; a malformed `target_ref` is recorded as
`target_ref_problem`, never echoed).

| Status | `code` | When |
|---|---|---|
| 404 | `not_found` | unknown run, no `ml_campaigns` row, or an `AuthProfile` outside the project |
| 409 | `llm_target_required` | a probe run (D9) |
| 409 | `campaign_not_terminal` | the campaign has not finished |
| 409 | `score_unavailable` (`reasons: [no_run_record]`) | the run has no `ml.run_record` |
| 409 | `job_in_flight` | a push for this (campaign run, foundry) is queued or running |
| 422 | `fixture_not_exportable` | the target detail or the frozen snapshot flags a fixture (D3) |
| 422 | `params_out_of_range` (`field: target_ref`) | a malformed rid, or none in the body and none configured |
| 422 | `auth_profile_kind_unsupported` | a profile that is not a bearer profile |
| 501 | `integration_disabled` (`integration: foundry`, `reason: disabled` or `misconfigured` with `rule`) | Foundry unset or refused by a settings rule; a configuration state, not `not_implemented` |
| 503 | `queue_unavailable` | enqueue failed, the two rows rolled back |

Admission writes the `integration.push` row with the Foundry host as `target`
and the allowlist verdict on the NEW follow-up run's chain, then the `Run`
(scanner `ml.integration_push`, the campaign's `target_id`, `parent_run_id`)
and the `Job` (type `integration.push`, detail without a credential), then
`apply_async` on `redsim.integration_push` (queue `default`, the one pool with
egress). `202 {run_id, job_ids, status_url, integration: "foundry",
campaign_run_id, target_ref, kind}`. The worker re-reads the settings, loads
the digest-checked record, refuses a fixture-flagged record, builds the
scorecard payload and runs it through the D9 guard (a bare MRI, a URL string,
a JWT-shaped or `Bearer` value, a model file name, raw bytes, `expected_gain`,
`reviewer_notes` or a readiness word refuse the push as `payload_refused`),
stores the exact bytes that leave as `ml.integration.payload` and
`ml.integration.rows`, decrypts the bearer token only then, pushes through the
Foundry Datasets v2 flow (create an `APPEND` transaction, upload
`scorecard.json` and `rows.jsonl`, commit; abort best-effort on failure) and
stores `ml.integration.receipt`. `integration.push.execute` carries host,
dataset rid, transaction rid, payload, rows and record digests, HTTP statuses,
file count and bytes, or on failure `step`, `http_status`, `error_class`,
`transaction_aborted` with `success=False` (no retry); `job.complete` closes
the chain. Proven against `tests/ml/fake_foundry_server.py` only: no push to a
real Foundry instance has been made (INTEROP-26), and the dataset push (the
second half of INTEROP-23) is not built (`PUSH_PAYLOADS` is `("scorecard",)`
and the roster's `payload` line describes the scorecard only).

## LLM probes (wave B2) {#llm-probes}

The LLM track (`llm-core` and `llm-api`, verified from `redsim/api/v1/llm.py`,
`redsim/services/ml_llm.py`, `redsim/workers/tasks/ml_llm.py`,
`redsim/ml/llm/` and `tests/ml/test_llm_routes.py` / `test_llm_core.py`)
runs garak 0.16.0 probes against an [LLM target](#register-an-llm-target)
through the Pythia gateway and reports a probe scorecard with k/n
denominators. A probe run is never a campaign: it has no `ml_campaigns` row,
no MRI, no grade and no subscore (D9), and `/campaign` and `/compare` refuse it
with `409 llm_target_required`.

### `GET /v1/llm/probes`

**Authenticated.** The committed probe catalog (`redsim/ml/llm/catalog.json`,
regenerated from the installed garak by `build_catalog_from_garak()` and read
with json and pydantic only): 103 probes across thirteen modules (`dan`,
`promptinject`, `latentinjection`, `encoding`, `donotanswer`, `goodside`,
`grandma`, `phrasing`, `divergence`, `exploitation`, `web_injection`,
`realtoxicityprompts`, `fitd`), each with `module`, `cls`, `short_id`, `tier`,
`goal`, `doc_uri`, tags, primary and extended detectors with their offline
flags, `honours_prompt_cap`, `prompt_source`, `data_files`,
`upstream_licence_note`, `sets` and a `status` of `offline`, `extended` or
`excluded` with its reason. Two sets: `redsim-core` (76 probes whose primary
detector is a string, trigger or regex matcher, the default) and
`redsim-extended` (85, opt-in: the core plus `latentinjection.LatentJailbreak`
and the eight `realtoxicityprompts` probes whose primary detector is a Hugging
Face classifier, with `requires` naming `REDSIM_LLM_PROBE_HF_DETECTORS=1` and a
pre-cached model directory). 18 rows are excluded with a visible reason:
`fitd.FITD` (HarmBench material, owner default LLM-08), `dan.AutoDAN` (drives
a separate red-team model), `grandma.GrandmaIntent` (intent-routed detectors)
and every uncapped `*Full` or `RepeatExtended` corpus variant whose capped
sibling exists. The body also carries `default_probe_set`,
`max_prompts_per_probe` (the deployment cap) and `launch_route`. `501
not_implemented` with the reason on a tree without the catalog package,
`503 ml_catalog_unavailable` on an import error.

### `POST /v1/models/{model_id}/probes`

**Membership, then `llm.probe.run` (remediator+).** `404` for an unknown or
deleted model. Body:

```jsonc
{
  "probe_set": "redsim-core",          // or probe_ids: ["dan.Dan_11_0", ...]; neither means redsim-core
  "max_prompts_per_probe": 16,         // 1 to 64 (REDSIM_LLM_PROBE_MAX_PROMPTS_PER_PROBE caps the deployment)
  "seed": 0,
  "detector_mode": "offline",          // offline | hf (needs REDSIM_LLM_PROBE_HF_DETECTORS=1 on the worker)
  "finding_hit_threshold": 0.2         // (0, 1]; a detector row at or above it becomes a finding
}
```

Admission (`services.ml_llm.admit_llm_probe_run`), in order: the target must
be an LLM target (`409 llm_target_required` for a classifier) in status
`available` (`409 model_load_refused`); its probe key must still be a live
bearer profile (`422 probe_key_required`); the catalog must be on the tree
(`501` with the reason, `503 queue_unavailable` when it cannot be read);
explicit `probe_ids` must all be runnable under the detector mode (unknown
ids, catalog-excluded ids and probes that need `detector_mode=hf` are refused
with the register's `unknown_probe`, `probe_excluded` and
`probe_detector_unavailable` reasons, spelled with the table codes
`probe_set_unknown` and `params_out_of_range` until they gain rows), a set is
admitted as its runnable members with `not_admitted` recorded
(`422 probe_set_unknown` for an unknown set); `max_prompts_per_probe` above
the deployment cap is `422 params_out_of_range`; one run per target at a time
(`409 job_in_flight`); a per-project daily quota
(`REDSIM_LLM_PROBE_MAX_RUNS_PER_PROJECT_PER_DAY`, default 10, `429` with
`retry_after`, spelled `rate_limited` until `llm_probe_quota_exceeded` has a
row). Then `authorize("llm.probe.run", gateway_url, allowlist)` with ids and
counts only, a `Run` (`scanner ml.llm_probe`, `stage_table.kind llm_probe`,
`probe_ids`) and a `Job` (type `llm.probe`, detail with the ids, settings,
`probe_short_ids`, `not_admitted`, `expected_garak_version` and
`prompt_estimate`, never a key), then `apply_async` on
`redsim.ml_llm_probe_run` (queue `default`); a broker failure deletes the
rows and answers `503 queue_unavailable`. `202`:

```json
{ "run_id": "run-…", "job_ids": ["job-…"], "status_url": "/v1/runs/run-…", "scorecard_url": "/v1/runs/run-…/llm-scorecard", "kind": "llm_probe" }
```

The worker (`redsim/workers/tasks/ml_llm.py`) refuses before any gateway
request when `REDSIM_DISABLE_LLM` is set (`llm_disabled`), when the project or
organisation LLM budget is spent (`budget_exceeded`) or when the profile is
gone (`auth_profile_missing`); checks the key's entitlement to the model
through `GET /v1/models` on the gateway (`llm.probe.entitlement` audit row,
`model_not_entitled` or `gateway_unreachable`); runs garak in a fresh
credential-minimised subprocess with the key in a 0600 file the child deletes
at once, the hard prompt cap enforced on every probe (garak's soft cap is
honoured by only some), library loggers raised so `garak.log` carries no
request headers and every written file scrubbed for the key; stores
`report.jsonl`, `hitlog.jsonl`, the digest HTML, the usage ledger and
`child_result.json` as `ml.llm.*` artifacts that are never parsed for text;
writes the scorecard, findings, rule candidates, reports and the
`llm.probe.execute.<probe>`, `llm.probe.score`, `report.render` and
`job.complete` rows. A failed or timed-out child keeps its evidence as
`ml.llm.partial.*`, projects nothing and fails the job.

### `GET /v1/runs/{run_id}/llm-scorecard`

**Membership.** The digest-checked `ml.llm.scorecard` artifact:
`kind: llm_probe`, the target and settings, `completeness` (`complete`,
`partial` or `none`), `families` sorted, each probe with counts sent, loaded
and after the cap and a `status` of `run`, `not_run` or `failed` with its
reason, each detector row `llm.<probe>.<detector>` with `n_evaluated`,
`n_hits` (garak's fails), `n_passed`, `n_none`, `hit_rate` (`null` exactly
when `n_evaluated` is 0, else validated equal to `n_hits / n_evaluated`) and
garak's confidence interval when present, `excluded_probes`, a `usage` block
(requests, statuses, retries, tokens, `cost_cents`, `unpriced_model`, the
model ids the gateway answered with, `tls_mode`), `limitations` (the D9
sentence, what a hit means, the detector approximation, the `guardrail_mode`
sentence, the prompt cap and seed, the detector mode, the garak version, the
excluded and not-run probes, the `pythia/auto` instability note, no
narrative, no safety claim) and the artifact digests. A model validator
walks the dump and refuses any `mri`, `grade`, `subscore`, `S_*`,
`robustness_index` or `weights` key, and no family rate is ever computed.
`409 llm_target_required` for a campaign run; `409 score_unavailable` with
the run status while the run is not terminal, when no scorecard exists, or
when the bytes do not match the recorded digest.

Findings (`services.ml_findings.project_llm_findings`): one per detector row
whose hit rate reaches `finding_hit_threshold`, `source_tool`
`redsim.ml/llm_probe`, severity derived from the hit rate and labelled so
(`>= 0.5` high, `>= 0.2` medium, `> 0` low), title and description with
denominators and no prompt text, `dedup_key`
`llm:<model>:<probe>:<detector>:<settings hash>`, idempotent per (run,
`scanner_finding_id`), a `review` block at `schema_blob.llm.review` that the
[review workflow](#review-workflow) accepts. Since wave B4 the rows carry
`finding_type: adversarial_llm` (`redsim/schema.py` `FindingType` gained the
literal additively; the `finding_kind` marker of the B2 rows stays readable). Candidate recommendations come from the
rule layer (`r.L1` jailbreaks, `r.L2` injection, `r.L3` encoding, `r.L4`
refusal policy, `r.L6` exploitation, `r.L7` divergence and format, and
`r.L5` always: rerun with another seed and a larger cap), every one
`status: candidate`, `narrative_source: rules`;
no LLM narrative is offered for probe results.

## Reports

### `GET /v1/runs/{run_id}/report.{ext}?snapshot=<id|version>`

**Membership on the run's project, then `report.export` (scanner+).** `{ext}` is
`md | json | html | pdf` (`pdf` since wave B2). For a campaign run the newest
non-archived snapshot's artifact of that format is served first (wave B2),
then the newest report `Artifact` row of that format (kind `report.<ext>`, or
the legacy `ml.report_<ext>`), each after its bytes are checked against the
recorded digest, with `ETag`. Runs without an artifact row fall back to the
blob key `runs/<run>/report.<ext>` and then the filesystem `output_dir` for
`md`, `json` and `html` only: a PDF is never served from the filesystem and
answers `404 report not yet rendered` until a render produced one. With
`?snapshot=<id or 1-based version>` exactly that immutable render is served
or refused (`404 snapshot_not_found`, `409 snapshot_archived` for a
non-admin, `404` when that render did not produce the format); nothing else
is tried.

HTML responses carry the strict headers:

```
Content-Security-Policy: default-src 'none'; style-src 'self' 'unsafe-inline'; img-src data:; base-uri 'none'; frame-ancestors 'none'; form-action 'none'
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
X-Frame-Options: DENY
Content-Disposition: inline
```

JSON and Markdown carry nosniff plus
`Content-Disposition: attachment; filename="redsim-<run>-report.<ext>"`; the
PDF is `application/pdf`, `attachment`, nosniff, `ETag` the sha256.

| Status | Meaning |
|---|---|
| 400 | ext outside `md`, `json`, `html`, `pdf` |
| 403 | no membership, or below `scanner` |
| 404 | run unknown, `report not yet rendered` (every `report.pdf` before a render), or `snapshot_not_found` |
| 409 `report_artifact_digest_mismatch` | the artifact bytes no longer match their digest |
| 409 `snapshot_archived` (`snapshot_id`) | `?snapshot=` names an archived snapshot and the caller is not admin |

The Markdown report has the six sections of spec 14.8 in order (configuration
and provenance, measurements with the MRI scorecard sub-block, observations,
interpretation, candidate recommendations, limitations followed by reviewer
notes). Every recommendation is a candidate with no measured effect. Since
wave B2 section 1 prints the
`schema_version` and a licence line (or "not recorded in the model or
dataset manifest"), the scoring line and the scorecard say "default vector"
or carry the **Non-default weights** badge with the vector,
section 6 ends with "No export-redaction policy was applied to this report"
(D006 open), and an LLM probe record embeds its scorecard section between
sections 2 and 3. `report.json` is the `CampaignRecord` dump. `report.pdf`
(wave B2, `redsim/ml/pdf.py`) typesets the same Markdown into reportlab
flowables with bundled DejaVu subsets, a third projection of the record and
never a recomputation, byte-identical for the same record and stamp, footer
with run id, schema version, stamp and page number; the six spec 14.8

B4 the campaign task's completion path renders `md`, `json`, `html` and `pdf`,
lists what it wrote on the `report.render` row and records the run's first
`report_snapshots` row over those artifact rows (REVIEW_REPORTS-16/-20); a
record the PDF renderer cannot typeset (reportlab `LayoutError` on a wide
measurement table) gets the three text formats and `pdf_unavailable` on the
row, so `report.pdf` is `404 report not yet rendered` only then.
`redsim.report_render` re-renders from the `ml.run_record` artifact with the
current reviewer notes after a `report.render` audit row and writes one
further `report_snapshots` row per render (version 2 onwards after a
completion snapshot).

### `POST /v1/runs/{run_id}/report.render` {#report-render}

**Membership, then `report.render` (scanner+)** (wave B2
`reports-compare-weights`; the B0 stub replaced). Body `{"formats":
["md", "json", "html", "pdf"]}` (optional, `validate_render_formats`). Audit
first: run lookup (`404`), a campaign row or an `ml.*` scanner required,
`409 campaign_not_terminal` and `409 job_in_flight` with `success=False` rows,
then the `report.render` audit row (`phase: admitted`, `job_id`, `formats`,
`requested_by`), then a `Job` of type `report.render` on the terminal run
(its status untouched), then the enqueue on `redsim.report_render` (a broker
outage is tolerated as for the finding action jobs). `202` JobHandle. The
worker renders every requested format, records each through
`run_state.record_artifact`, looks the `Artifact` ids up by (run, kind,
sha256) and writes one `ReportSnapshot` row (`snap-<hex>`, `artifact_ids`,
`record_sha256`, `rendered_at` the stamp printed in the documents,
`created_by`).

### Snapshots {#snapshots}

Wave B2 (`redsim/services/reports.py`, `redsim/api/v1/reports.py`; the two
B0 stubs left `redsim/api/v1/batches.py`). A snapshot is an immutable row
over content-addressed artifacts; bytes are never deleted.

- `GET /v1/runs/{run_id}/snapshots` (**membership**): newest first,
  `{run_id, snapshots: [{id, version, run_id, project_id, rendered_at,
  created_by, archived, artifact_ids, formats: {ext: {artifact_id, kind,
  sha256, size_bytes, content_type}}, record_sha256}], count}`; the
  `archived` flag is visible to every member.
- `GET /v1/runs/{run_id}/snapshots/{ref}` (**membership**): one snapshot by
  id or 1-based chronological version; `409 snapshot_archived` unless the
  caller passes the admin gate.
- `POST /v1/runs/{run_id}/snapshots/{ref}/archive` and `/restore`
  (**`target.manage`**, admin): the soft flag, audited as
  `report.snapshot.archive` / `report.snapshot.restore` (snapshot id,
  version, record digest, artifact count, before and after flags) before the
  flag flips; a no-op is still audited and answers `changed: false`.

## Exports {#exports}

### `GET /v1/exports?project=<id>&limit=<n>`

**Authenticated; membership on `?project=` when given, else the caller's
memberships (every project for a system principal).** Added 2026-09-09 for
the web `/exports` page (spec 18.1 addendum). One row per campaign run
(`Run.scanner` `ml.campaign`, each row `kind: "campaign"`), newest first,
with the state of everything the run can export: the report formats of spec
14.8 and 17.1 and the adversarial dataset of spec 27.1. Follow-up export
runs, probe runs, validation runs and pentest-era runs are not listed. There
is no `kind` query parameter. `limit` is 1 to 500, default 50. A `limit`
outside the range is `422 params_out_of_range` naming the field. The route lists and
writes nothing: no audit row, no `Run`, `Job` or `Artifact`. Downloads stay
on [`GET /v1/runs/{id}/report.{ext}`](#reports) (`report.export`) and
`GET /v1/datasets/{id}`; the actions stay on
[`POST /v1/runs/{id}/report.render`](#report-render) (`report.render`) and
[`POST /v1/runs/{id}/dataset`](#dataset-export) (`dataset.export`), each with
its own gate and audit row, so a viewer reads the inventory the way a viewer
reads `GET /v1/runs`. Rows carry ids, digests, sizes and counts only, never a
score (spec 15.7).

```json
{
  "exports": [
    {
      "run_id": "run-…", "project_id": "…", "kind": "campaign", "status": "succeeded",
      "terminal": true, "created_at": "…+00:00", "completed_at": "…+00:00",
      "model": {"target_id": "…", "name": "…", "value": "bundled:…", "modality": "image", "fixture": false},
      "reports": {
        "run_id": "run-…",
        "formats": {"md": {"artifact_id": "…", "kind": "report.md", "sha256": "…", "size_bytes": 0,
                           "source": "snapshot", "snapshot_version": 1},
                    "json": {"…": "…"}, "html": {"…": "…"}, "pdf": null},
        "available": ["md", "json", "html"], "missing": ["pdf"],
        "snapshot_count": 1,
        "latest_snapshot": {"id": "snap-…", "version": 1, "rendered_at": "…", "archived": false},
        "render_in_flight": false
      },
      "dataset": {
        "format": "croissant-parquet", "status": "exported",
        "manifest_artifact_id": "…", "manifest_sha256": "…", "files": 3, "bytes": 0, "card": true,
        "job_id": null, "follow_up_run_id": null, "error": null, "blockers": []
      }
    }
  ],
  "count": 1, "report_formats": ["md", "json", "html", "pdf"],
  "dataset_format": "croissant-parquet", "limit": 50
}
```

- `reports.formats.<ext>` is the artifact of that format in the newest
  non-archived snapshot (`source: snapshot` with its `snapshot_version`),
  else the newest report `Artifact` row of that format (`source: artifact`,
  the same fallback the report route uses), else `null`.
  `render_in_flight` is true while a `report.render` job on the run is queued
  or running.
- `dataset.status` is `exported` when the run carries an `ml.dataset.manifest`
  artifact (`files` counts the `ml.dataset.parquet` rows, `bytes` sums them
  with the manifest, `card` says whether the template card was written);
  `queued` or `running` while a `dataset.export` job naming the run in its
  detail is active (`job_id`, `follow_up_run_id`); `failed` with the job's
  `error` when the last one failed; else `not_exported`. `blockers` lists why
  the admission would refuse a new export: `not_terminal`, `run_failed`,
  `fixture_target`, `no_slices`. An empty list with `not_exported` or
  `failed` means the page may offer the action; the admission still decides.
- Timestamps are the audit chain's canonical UTC `+00:00` isoformat, so a
  sqlite harness and Postgres read the same.

### `GET` and `PUT /v1/projects/{slug}/ml-scoring` {#ml-scoring}

Wave B2 (`reports-compare-weights`, REVIEW_REPORTS-28; the `projects.ml_scoring`
column of migration `0011`). `GET` (**any member**) returns the effective

```jsonc
{ "project": "default", "project_id": "…", "source": "default", "ml_scoring": { "version": "…", "weights": { "S_acc": 0.35, "S_asr": 0.25, "S_eps": 0.20, "S_conf": 0.10, "S_expl": 0.10 }, "…": "…" }, "non_default_weights": false }
```

override is read at campaign admission ([Start a
campaign](#start-a-campaign)) and frozen into the config, so a non-default
vector puts the **Non-default weights** badge on the scorecard and the
report and makes the campaign comparable only with campaigns that share it.

## Auth profiles

Stored authentication material, Fernet-encrypted at rest and never returned by
any endpoint. Since wave B2 a `bearer` or `header` profile carries the
credential of a black-box predict endpoint and a `bearer` profile the Pythia
probe key of an LLM target; the worker resolves it at job pickup
(`services.auth_profiles.resolve_auth_for_scan`) and only the broker or the
probe child's 0600 key file ever sees it. Writes are gated on
`auth_profile.manage` (admin) and emit chained `auth_profile.create` /
`auth_profile.delete` events. Since wave B4 `DELETE /v1/auth-profiles/{id}`
answers `409 auth_profile_in_use` with `target_ids` while a live
(non-deleted) `ml_model_endpoint` target of the project names the profile,
after a `success=False` `auth_profile.delete` row naming the same ids, so a
queued campaign or probe run can never resolve a dangling credential
(ENDPOINT-18); delete or re-point the targets first.

### `GET /v1/auth-profiles?project=<id>`

List a project's profiles, non-secret fields only. **RBAC: project membership.**

### `POST /v1/auth-profiles`

```jsonc
{ "project_id": "proj-a", "name": "endpoint-bearer", "kind": "bearer", "config": {}, "secret": "the-token" }
```

The chained `auth_profile.create` event is written before the row, and the
secret is encrypted before either happens, so a missing
`REDSIM_AUTH_PROFILES_KEY` fails closed. `201` on success, `409` on a duplicate
`(project_id, name)`.

### `DELETE /v1/auth-profiles/{profile_id}`

`204`, `404` when unknown, or `409 auth_profile_in_use` (`target_ids`, `field: profile_id`) while a live endpoint or LLM target references the profile (wave B4). **RBAC: `admin` on the profile's project.**

## Cross-cutting headers

| Header | When set |
|---|---|
| `X-Redsim-Request-ID` | Echoed back on every response. Supply your own to control correlation. |
| `X-Redsim-CSRF` | Required on cookie-authenticated mutations (POST/PUT/PATCH/DELETE). |
| `Idempotency-Key` | Request header honoured since wave B2 on the mutating ML routes, see below. |
| `Idempotency-Replayed: true` | Response header on a replay served from the stored response. |
| `Content-Security-Policy` | Report HTML responses (strict report policy) and `GET /v1/artifacts/{id}` (`default-src 'none'`). |
| `X-Content-Type-Options: nosniff` | Every report and artifact response. |
| `ETag` | Report and artifact responses: the recorded sha256. |

### `Idempotency-Key` {#idempotency-key}

Wave B2 (`redsim/api/middleware/idempotency.py`, added innermost inside the
tenant scope; `tests/test_idempotency.py`; the `idempotency_keys` table of
migration `0011`). A pure ASGI middleware that passes every request through
unless it is a `POST`, `PUT`, `PATCH` or `DELETE` under `/v1/models`,
`/v1/findings`, `/v1/runs`, `/v1/campaigns` or `/v1/datasets` carrying the
header (`DELETE /v1/models/{id}` and the model row itself, the
`/v1/campaigns/batch/{id}/...` routes and `POST /v1/findings`, keyed through
the body's `run_id`, included; `tests/test_idempotency.py` reads every
mutating route out of the OpenAPI document and asserts each ML-prefixed one
has a resolution strategy, with only `/v1/targets`, `/v1/auth-profiles` and
`/v1/projects` mutations passing through). Identity is the project (resolved
from the path row, the body's `project_id` or `?project=`), the principal (the app's `get_current_user`
override, else the bearer or cookie) and the key; the stored key is
`sha256(principal | header)`, so the raw header never lands in the table and
another principal's identical key is a different identity. `request_sha256`
is canonical over method, path, sorted query and canonical-JSON body. A miss
reserves the `(project_id, key)` row with `response_status` 0, the route
runs on a replayed receive, a 2xx JSON response up to 64 KB is stored and
later replayed with `Idempotency-Replayed: true` and no second `Run`, `Job`,
audit row or enqueue; any other outcome releases the reservation. A key
outside 1 to 255 characters is `422`; rows older than 24 h are a miss; a
database failure in the lookup is a logged pass-through, never a `500`.

| Status | `code` | When |
|---|---|---|
| 409 | `idempotency_key_reused` (`request_sha256`) | the same key with a different route or body |
| 409 | `idempotency_conflict` | the same key while the original request is still reserved and unfinished |
