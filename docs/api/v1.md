# HTTP API reference (`/v1/*`)

This page enumerates every HTTP route the API exposes. For the auth
header semantics see [`docs/architecture/auth.md`](../architecture/auth.md);
for the RBAC role matrix see the same doc's "RBAC" section.

Every route below requires either an `Authorization: Bearer …` header
**or** a valid `aegis_api_session` cookie — except `/health`, which
is unauthenticated. Cookie-authenticated mutations additionally
require the `X-Aegis-CSRF` header that matches the `aegis_csrf`
cookie (see [F14b](../architecture/auth.md#csrf-double-submit-cookie)).

Routes are grouped by RBAC tier:

| Tier              | Sections                                                       |
|-------------------|----------------------------------------------------------------|
| **Open**          | [Health](#health)                                              |
| **Authenticated** | [Runs](#runs) · [Findings](#findings) · [Tickets (list)](#tickets) · [Target verification (read)](#target-verification) · [Reports](#reports) · [Exports](#exports) · [Projects](#projects) · [Orgs](#orgs) · [WebSocket](#websocket) |
| **Scanner+**      | [Scans](#scans)                                                |
| **Remediator+**   | [Fix](#fix) · [Verify](#verify) · [Runs cancel](#runs-cancel) · [Tools (`read`)](#tools) · [Agents (`run`)](#agents) · [Tickets (sync / refresh)](#tickets) |
| **Approver+**     | [Fix (`apply=true`)](#fix) · [Agents (`execute=true`)](#agents) · [Tools (`active`, `execute=true`)](#tools) |
| **Admin**         | [Targets](#targets) · [Auth profiles](#auth-profiles) · [Target verification (verify)](#target-verification) · [Audit verify](#audit) · [Logs](#logs) · [Project settings](#project-settings) |
| **External (HMAC)** | [GitHub webhooks](#github-webhooks)                           |

## Runs

```json
      "id": "run-abc123",
      "project_id": "proj-a",
      "status": "succeeded",
      "scanner": "strix",
      "mode": "api",
      "created_at": "2026-05-28T12:00:00+00:00",
      "created_by": "user:alice@example.com"
    }
  ],
  "next_cursor": "run-xyz789",
  "count": 1
}
```

### `GET /v1/runs/{run_id}`

One run with summary.

```json
{
  "run": { "id": "run-abc123", … },
  "jobs": [ { "id": "job-…", "type": "scan.start", "status": "succeeded" } ],
  "findings_count": 12,
  "stages": [ { "name": "scan.start", "mode": "live", "success": true } ]
```

## Tickets

Bidirectional sync of a finding into an external tracker (Jira /
ServiceNow / Linear). The provider is selected at process start via
`AEGIS_TICKET_PROVIDER` (default `none` = no-op); see
[Integrations § ticket sync](../integrations/index.md#bidirectional-ticket-sync)
for the per-provider credentials. No response ever carries a secret.

### `POST /v1/findings/{finding_id}/ticket`

Push (create-or-update) the finding's ticket in the configured tracker.
**RBAC: `remediator+`.** Upserts a `FindingTicket` keyed on
`(finding_id, provider)`, so re-syncing the same finding is idempotent.
Emits a secret-free `ticket.sync` audit event (provider + external id).

Response (`201` on first sync, `200` on a re-sync that updated the row):

```json
{
  "id": "tkt-ab12cd34ef56",
  "finding_id": "f-uuid",
  "project_id": "proj-a",
  "provider": "jira",
  "external_id": "SEC-123",
  "url": "https://acme.atlassian.net/browse/SEC-123",
  "status": null,
  "synced_at": "2026-06-11T12:00:00+00:00"
}
```

Errors:

| Status | Meaning                                                                       |
|--------|-------------------------------------------------------------------------------|
| 403    | RBAC failure (`remediator+`)                                                  |
| 404    | finding unknown                                                               |
| 409    | no ticket provider configured (the default) OR the provider push failed       |

### `GET /v1/findings/{finding_id}/tickets`

List the tickets recorded for a finding (most-recent first). **RBAC:
project membership on the finding's project.**

```json
{
  "tickets": [
    { "id": "tkt-…", "provider": "jira", "external_id": "SEC-123",
      "url": "https://…/browse/SEC-123", "status": "In Progress",
      "synced_at": "2026-06-11T12:00:00+00:00" }
  ],
  "count": 1
}
```

### `POST /v1/findings/{finding_id}/tickets/{ticket_id}/refresh`

Pull the external status into the row — the inbound half of the
bidirectional sync. **RBAC: `remediator+`.** Re-queries the tracker and
writes the current `status` back onto the `FindingTicket`. Returns the
updated ticket (same shape as the sync response).

Errors:

| Status | Meaning                                                                       |
|--------|-------------------------------------------------------------------------------|
| 403    | RBAC failure (`remediator+`)                                                  |
| 404    | finding or ticket unknown (or the ticket isn't on this finding)               |
| 409    | no ticket provider configured OR the status pull failed                       |

## Scans

### `POST /v1/scans`

Enqueue a scan. **RBAC: `scanner+` on the target project.** Emits a
chained `scan.start` audit row **before** the Celery task is touched.

Body:

```jsonc
{
  "target": "http://localhost:3000",
  "project_id": "proj-a",            // defaults to "default"
  "scanner": "strix",                 // strix | trivy | semgrep | nuclei | zap | codeql | bandit | grype | checkov | trufflehog | sonarqube | syft | bumblebee | deepsec
  "instruction": "Focus on the /login endpoint.",   // optional, scanner-dependent
  "auth_profile_id": "authprof-…",    // optional: authenticated DAST (zap / nuclei) — see Auth profiles
  "override_authorized": false        // bypasses target-allowlist check
}
```

`auth_profile_id` references a stored [auth profile](#auth-profiles);
only the **id** travels through admission and `Job.detail` — the worker
decrypts the secret at execution time and the `zap` / `nuclei` adapters
replay it as a header (other scanners ignore it). See
[`docs/ops/authenticated-dast.md`](../ops/authenticated-dast.md).

Response (`200`):

```json
{
  "run_id": "run-abc123",
  "job_id": "job-456",
  "status_url": "/v1/runs/run-abc123"
}
```

Errors:

| Status | Meaning                                                                       |
|--------|-------------------------------------------------------------------------------|
| 400    | `target` missing                                                              |
| 403    | RBAC failure OR target not on allowlist (and `override_authorized=false`)     |
| 401    | Authentication required                                                       |

## Agents

### `POST /v1/agents/{agent_name}/run`

Enqueue a registered CAI agent. Admission-only, mirroring `POST /v1/scans`: a
chained audit row is emitted **before** the Run/Job rows and **before** Celery
is touched, so a crash mid-enqueue can never leave a row without a matching
chain event. The `agent_run` Celery task does the execution (re-authorize →
`dispatch(agent_name)`); no dispatch happens in the route.

`agent_name` is one of the **36 wired agents** — e.g. `codeagent`,
`blueteam_agent`, `recon`, `bug_bounter`, `red_teamer`, `web_pentester`,
`dfir`, `retester`, `reporter`, the 8 breadth CAI agents (`ctf_agent`,
`app_logic_mapper`, …), and the 12 authored specialists (`cloud_recon`,
`osint_collector`, …) — or one of the **5 multi-agent patterns**
(`offsec_pattern`, `redteam_swarm`, `bb_triage_swarm`,
`red_blue_shared_context`, `red_blue_split_context`; see below), for **41**
dispatchable entries in all.

**The `execute` flag selects the RBAC action and whether the agent actually
runs**, per the [effect-class gate](../adr/0004-unified-effect-class-gate.md):

- **`execute=false` (default)** — `agent.run` action, **RBAC: `remediator+`**.
  A `read`-effect agent (recon, SAST, reporting) runs and returns its findings.
  An `active`-effect agent (exploitation, live hardening) is **not** run: the
  worker's `dispatch()` returns `status="pending_approval"` carrying a structured
  attack/hardening **plan** for review — nothing irreversible happens.
- **`execute=true`** — `agent.execute` action, **RBAC: `approver+`** (mirrors
  `apply=true` on fixes). The gated agent is actually invoked.

A `read`-effect agent ignores `execute` — it always just runs (the target
allowlist is its only gate). Effect is a per-agent property, **not** a function
of domain: an `android_sast` agent is offensive-by-domain but `read`-effect; a
`retester` re-fires exploits so it is `active`-effect.

**Multi-agent patterns.** Five composite entries coordinate several CAI agents
behind one dispatch: `offsec_pattern` (a parallel offensive sweep), the
`redteam_swarm` / `bb_triage_swarm` handoff swarms, and two red/blue parallel
patterns (`red_blue_shared_context`, `red_blue_split_context`) that run a
red-team attack alongside a blue-team responder. They run **only when
dispatched by name** — a normal single-agent run never triggers one (no
auto-swarm). All five are `active`-effect, so the same gate applies: without
`execute=true` they return a `pending_approval` plan and no agent runs.

**Live Kali tool belt (MCP).** When `execute=true`, the active offensive
specialists (`bug_bounter`, `red_teamer`, `web_pentester`) can reach the live
Kali tool belt at run time over an SSE MCP connection to `config.mcp_kali_url`.
The read-only `recon` agent is deliberately excluded — the belt carries active
tools, and recon stays read-only.

Body:

```jsonc
{
  "prompt": "Exploit the SQLi on /login.",  // required
  "project_id": "proj-a",                    // defaults to "default"
  "execute": false,                          // true → actually run an active agent (approver+)
  "target": "http://localhost:3000",         // optional; allowlist-checked if present
  "finding_id": "fnd-123",                   // optional
  "repo_path": "/work/repo",                 // optional
  "override_authorized": false               // bypasses target-allowlist check
}
```

Response (`200`):

```json
{
  "run_id": "run-abc123",
  "job_id": "job-456",
  "status_url": "/v1/runs/run-abc123"
}
```

When an `active` agent is enqueued with `execute=false`, the run completes with
a `pending_approval` result whose payload is the proposed plan (no live agent
runs to produce it):

```json
{
  "status": "pending_approval",
  "plan": {
    "agent": "red_teamer",
    "domain": "offensive",
    "effect": "active",
    "target": "http://localhost:3000",
    "intent": "Exploit the SQLi on /login.",
    "gated": true,
    "required_role": "approver",
    "to_execute": "re-invoke with execute=true (requires the approver role)",
    "note": "Executing will run active exploitation / attack tooling against the target."
  }
}
```

Errors:

| Status | Meaning                                                                       |
|--------|-------------------------------------------------------------------------------|
| 400    | `prompt` missing                                                              |
| 403    | RBAC failure (`remediator+` for `run`; `approver+` for `execute=true`) OR target not on allowlist (and `override_authorized=false`) |
| 401    | Authentication required                                                       |

## Fix

### `POST /v1/findings/{finding_id}/fix`

Enqueue a remediation. **RBAC: `remediator+` for generate;
`approver+` when `apply=true` or `open_pr=true`.**

Body:

```jsonc
{
  "strategy": "patch",       // patch | live | deps | agentic
  "apply": false,             // commit the change (approver+)
  "open_pr": false,           // let the engine open a PR (agentic only; implies apply; approver+)
  "repo": "/path/to/repo",    // worker-side filesystem path
  "override_authorized": false // bypasses target-allowlist check at execution
}
```

All four strategies share **one** human-in-the-loop gate (the
[effect-class gate](../adr/0004-unified-effect-class-gate.md)) — `apply`
defaults `false`, so a fix always **proposes** first:

- **`patch`** — generate a unified diff for a code finding. `apply=false` →
  `pending_apply` (diff only); `apply=true` → rollback-safe local commit.
- **`live`** — blue-team live hardening of a running target. `apply=false`
  returns a hardening **plan** (`pending_approval`) and the blue-team agent is
  **never** invoked; `apply=true` runs the hardening.
- **`deps`** — dependency-bump patch; same gate as `patch`.
- **`agentic`** — drives the vendored vulnerability-fixer engine. `apply=false`
  → engine runs diff-only (`--no-push --no-pr`), returns `pending_apply`;
  `apply=true` → rollback-safe local commit; `apply=true, open_pr=true` →
  **the engine opens the human-reviewed PR itself** (the PR review *is* the
  gate). PR mode needs `GITHUB_TOKEN` in the worker environment (passed via the
  subprocess env, never argv); absent it the engine soft-degrades to a failed
  outcome.

Response (`200`):

```json
{ "job_id": "job-789", "run_id": "run-abc123" }
```

## Verify

### `POST /v1/findings/{finding_id}/verify`

Re-run the finding's PoC against the target. **RBAC:
`remediator+`.** The verify outcome (`verified` /
`still_vulnerable` / `inconclusive`) is mirrored onto
`findings.validation_state` by the worker (F11).

Response (`200`):

```json
{ "job_id": "job-…" }
```

## Runs cancel

### `POST /v1/runs/{run_id}/cancel`

Cancel an in-flight run. **RBAC: `remediator+`.** Best-effort
`celery.revoke` on every queued / running job; the worker re-checks
on each heartbeat. Emits a chained `run.cancel` event.

Response (`200`):

```json
{ "run_id": "run-abc123", "status": "cancelled", "jobs_cancelled": 2 }
```

## Tools

### `POST /v1/tools/kali/{tool}`

Invoke a Kali tool via mcp-kali. Per-tool forensic audit row emitted via the
canonical chain (digests + refs, not raw output — see
[`audit-chain.md`](../architecture/audit-chain.md)).

`{tool}` is one of `nmap | nikto | sqlmap | gobuster | dirb | hydra | john | wpscan | enum4linux | metasploit`. The generic `command` tool is
disabled by default and returns `403` for **every** role.

Each tool carries an [effect class](../adr/0004-unified-effect-class-gate.md);
an unlisted tool fails **safe** (treated as `active`):

- **`read` tools** (`nmap`, `nikto`, `gobuster`, `dirb`, `enum4linux`, `john`)
  — recon/enumeration. `tool.invoke` action, **RBAC: `remediator+`**. Run
  immediately.
- **`active` tools** (`sqlmap`, `hydra`, `metasploit`, `wpscan`) — attack /
  state-changing. Gated like an `active` agent: `execute=false` (default)
  returns `status="pending_approval"` and the tool is **not** run; `execute=true`
  runs it and requires **RBAC: `approver+`**.

Body:

```jsonc
{
  "params": { "target": "127.0.0.1", "scan_type": "-sV" },
  "execute": false   // active tools only: true → actually run (approver+)
}
```

Response (`200`) for a `read` tool, or an `active` tool with `execute=true`:

```json
{
  "success": true,
  "tool": "nmap",
  "return_code": 0,
  "stdout": "…",          // truncated for the response; full in blob store
  "stderr": ""
}
```

Response (`200`) for an `active` tool with `execute=false`:

```json
{
  "tool": "sqlmap",
  "status": "pending_approval",
  "effect": "active",
  "params": {},
  "message": "active tool: resubmit with execute=true (requires the approver role)"
}
```

## Reports

### `GET /v1/runs/{run_id}/report.{ext}`

Stream the run's report. `{ext}` is one of `md | json | html`.

**RBAC: project membership on the run's project.** (Read tier — any
role is sufficient.)

HTML responses carry the strict v0.4.0 F14d security headers:

```
Content-Security-Policy: default-src 'none'; style-src 'self' 'unsafe-inline'; img-src data:; base-uri 'none'; frame-ancestors 'none'; form-action 'none'
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
X-Frame-Options: DENY
Content-Disposition: inline
```

JSON / Markdown carry nosniff + `Content-Disposition: attachment;
filename="aegis-<run>-report.<ext>"`.

Errors:

| Status | Meaning                                                                       |
|--------|-------------------------------------------------------------------------------|
| 400    | unknown ext                                                                   |
| 403    | caller has no membership on the run's project                                 |
| 404    | run unknown or report not yet rendered                                        |

## Orgs

### `GET /v1/orgs/{org_id}/cost?days=<n>` {#orgs-cost}

Per-Organization LLM cost / chargeback breakdown. **RBAC: membership on
any project in the org** (`ensure_org_access`) — cost visibility is
something a tenant sees for its *own* org, not a cross-tenant surface, so
it is **not** admin-gated.

Query params:

| Param  | Default | Range    | Meaning                                                       |
|--------|---------|----------|---------------------------------------------------------------|
| `days` | `30`    | `1`–`366` | Trailing window for the breakdowns. Out of range → `400`.    |

The breakdown window is the trailing `days`; the **budget block is always
the current UTC calendar month**, so it lines up with the monthly cap
regardless of the breakdown window. Costs are in **cents**.

Response (`200`):

```json
{
  "org_id": "org-1",
  "days": 30,
  "total_cents": 18750,
  "call_count": 412,
  "by_day":   { "2026-06-09": 1200, "2026-06-10": 1750 },
  "by_model": { "gpt-4o": 16000, "gpt-4o-mini": 2750 },
  "by_task":  { "patch": 14000, "report_summarize": 4750 },
  "budget": {
    "monthly_cap_cents": 50000,
    "month_spent_cents": 18750,
    "remaining_cents": 31250
  }
}
```

When the org has no `monthly_llm_budget_cents` set, `monthly_cap_cents`
and `remaining_cents` are `null` (uncapped); `month_spent_cents` is still
reported.

Errors:

| Status | Meaning                                                             |
|--------|---------------------------------------------------------------------|
| 400    | `days` outside `1`–`366`                                            |
| 403    | caller has no membership on any project in the org                  |
| 404    | org unknown                                                         |
| 401    | Authentication required                                            |

The web **/cost** dashboard renders this endpoint.

## Target verification

Prove the operator controls a target before its `verified` flag is set.
The method is chosen by `Target.kind` — DNS TXT for `url`, GitHub App
linkage for `github_repo`, unsupported for `image`. See
[Integrations § ownership verification](../integrations/index.md#cloud-target-ownership-verification)
for the token derivation and `AEGIS_VERIFY_SECRET`. Neither response nor
the audit event ever carries the secret.

### `GET /v1/targets/{target_id}/verification`

Return the instructions to satisfy. **RBAC: project membership.** For a
`url` target it returns the TXT `record_name` (the host) and `record_value`
(the per-target token); for `github_repo` it returns the App-installation
linkage required.

```json
{
  "target_id": "target-ab12cd34ef56",
  "kind": "url",
  "verified": false,
  "project_id": "proj-a",
  "method": "dns-txt",
  "record_type": "TXT",
  "record_name": "staging.example.com",
  "record_value": "aegis-site-verification=4f9c…",
  "instructions": "Add a DNS TXT record on staging.example.com with the value '…', then POST to this target's /verify endpoint."
}
```

### `POST /v1/targets/{target_id}/verify`

Run the ownership check. **RBAC: `admin` (`TARGET_MANAGE`) on the target's
project.** On success sets `verified=true`; emits a secret-free
`target.verify` audit event either way (records kind + method + matched).

Response (`200`, check passed):

```json
{
  "verified": true,
  "method": "dns-txt",
  "detail": "matched TXT record on staging.example.com",
  "target_id": "target-ab12cd34ef56"
}
```

Errors:

| Status | Meaning                                                                       |
|--------|-------------------------------------------------------------------------------|
| 403    | RBAC failure (`admin`)                                                        |
| 404    | target unknown                                                                |
| 422    | well-formed request, but ownership not yet proven (TXT absent / App not installed / `image` kind); `verified` left untouched |

## Auth profiles

Stored authentication material for authenticated DAST scans (see
[`docs/ops/authenticated-dast.md`](../ops/authenticated-dast.md)).
Secrets are Fernet-encrypted at rest and **never returned by any
endpoint**; writes are gated on the `auth_profile.manage` action
(admin, mirroring target management) and emit chained
`auth_profile.create` / `auth_profile.delete` audit events.

### `GET /v1/auth-profiles?project=<id>`

List a project's auth profiles. **RBAC: project membership.** Only
non-secret fields are returned.

```json
{
  "auth_profiles": [
    {
      "id": "authprof-1a2b3c4d5e6f",
      "project_id": "proj-a",
      "name": "juice-shop-login",
      "kind": "form",
      "config": {
        "login_url": "http://localhost:3000/rest/user/login",
        "username_field": "email",
        "password_field": "password",
        "username": "scanner@aegis.local"
      },
      "created_at": "2026-06-10T12:00:00+00:00"
    }
  ],
  "count": 1
}
```

### `POST /v1/auth-profiles`

Create an auth profile. **RBAC: `admin`** (`auth_profile.manage`).
Emits a chained `auth_profile.create` event **before** the row insert;
the secret is encrypted before either happens, so a missing
`AEGIS_AUTH_PROFILES_KEY` fails closed without a half-state.

```jsonc
{
  "project_id": "proj-a",        // defaults to "default"
  "name": "juice-shop-login",    // unique per project
  "kind": "form",                 // form | bearer | header | cookie
  "config": { "login_url": "…" }, // non-secret fields, by kind (below)
  "secret": "the-password"        // write-only; never echoed back
}
```

`config` keys by kind (the `secret` is everything else):

| Kind     | `config` keys                                              | `secret`         |
|----------|-------------------------------------------------------------|------------------|
| `form`   | `login_url`, `username_field`, `password_field`, `username` | the password     |
| `bearer` | *(none)*                                                    | the bearer token |
| `header` | `header_name`                                               | the header value |
| `cookie` | `cookie_name`                                               | the cookie value |

Response (`201`): the profile's non-secret fields, same shape as the
list entries above.

Errors:

| Status | Meaning                                                                       |
|--------|-------------------------------------------------------------------------------|
| 403    | RBAC failure (`admin` required)                                               |
| 409    | a profile with this `(project_id, name)` already exists                       |

### `DELETE /v1/auth-profiles/{profile_id}`

Remove an auth profile. **RBAC: `admin` on the profile's project.**
Emits a chained `auth_profile.delete` event. Response: `204`; `404`
if the profile is unknown.

## Audit

### `GET /v1/audit/verify?all=1&run=<run>&project=<id>`

Walk one or more chains and confirm every hash links. **RBAC:
`admin`.** Emits a chained `audit.verify` event of its own.

Response:

```json
{
  "chains": [
    { "chain_id": "run:run-abc",  "verified": true, "event_count": 42,
      "head_hash": "47b1a9…" },
    { "chain_id": "project:proj-a", "verified": true, "event_count": 7,
      "head_hash": "fe2c01…" }
  ]
}
```

On a broken chain the response carries `verified: false` and
`broken_at_seq: <n>` so an operator knows where to look.

## WebSocket

### `WS /v1/runs/{run_id}/events`

Subscribe to live stage events for a run (Redis pub/sub backed).

Auth sources, in order:
1. `Sec-WebSocket-Protocol: aegis.bearer.<token>` (recommended for
   programmatic clients; the server echoes it back).
2. `Authorization: Bearer …` header.
3. `aegis_api_session` cookie.

Frame shape:

```jsonc
{
  "type": "stage",
  "name": "scan.start",
  "mode": "live",
  "success": true,
  "detail": "strix returned 3 finding(s)"
}
```

Heartbeat frames (`{"type":"heartbeat"}`) keep the connection alive
when no real events are pending.

Close codes:

| Code | Reason                                                       |
|------|--------------------------------------------------------------|
| 1008 | origin not allowed / auth required / no project membership / run not found |

## GitHub webhooks

### `POST /v1/webhooks/github`

Receives `pull_request`, `push`, `installation` events from the
GitHub App. Verified by HMAC against `AEGIS_GITHUB_WEBHOOK_SECRET`;
deliveries deduplicated by `X-GitHub-Delivery` (10-min TTL set).

For `pull_request` events the response includes the structured PR
scope + restricted-mode decision (see
[`docs/security/fork-prs.md`](../security/fork-prs.md)):

```json
{
  "event": "pull_request",
  "delivery_id": "9bc8…",
  "action": "opened",
  "received": true,
  "scope": { "repo": "acme/widget", "pr_number": 99, "fork": true },
  "restricted_mode": "fork.restricted=true"
}
```

## Cross-cutting headers

| Header                | When set                                                                          |
|-----------------------|-----------------------------------------------------------------------------------|
| `X-Aegis-Request-ID`  | Echoed back on every response; supply your own to control correlation.            |
| `X-Aegis-CSRF`        | Required on cookie-authenticated mutations (POST/PUT/PATCH/DELETE).                |
| `Content-Security-Policy` | Set on report HTML responses (F14d). Not set elsewhere.                       |
| `X-Content-Type-Options: nosniff` | Set on every report / export response.                                |

## Error envelope

FastAPI's default `{"detail": "..."}` shape applies everywhere unless
otherwise stated. `4xx` and `5xx` responses are always JSON.

Common patterns:

- `401 { "detail": "authentication required" }` — no bearer + no cookie.
- `403 { "detail": "CSRF token missing or mismatched" }` — F14b.
- `403 { "detail": "role '<role>' cannot perform '<action>' on project <p>" }` — RBAC.
- `404 { "detail": "run not found" }` — `ensure_run_access`.
- `429` — rate limit (per-user or per-project token bucket).
